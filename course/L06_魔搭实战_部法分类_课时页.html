1这一课做什么

结论把 18,338 条「问题→部法」训练对喂给 Qwen3-1.7B，在魔搭免费 GPU 上训一个 50 选 1 的分类器。

这条链和你之前跑过的微调没有本质差别，只是任务从「生成一段文本」换成了「输出一个词」。

对比项生成任务（改写 / 问答）这一课（50 类分类）
训练数据几百到几千条 demo18,338 条，约 6 MB
输出长度几十到几百字一个部法名，2~10 个 token

怎么算学会只能人眼看像不像准确率，一算就有
训练耗时十几分钟约 1 小时（两轮）
这一课结束时，你手上有的三样东西
模型
一个 LoRA 适配器，几十 MB，能卸能装，不占 3 GB 的基座空间
数字
zero-shot 与微调后两组 accuracy / macro-F1 / top-3
尺子

  • 分类任务比生成任务轻：输出一个词，max_length 512 就够。
  • 18,338 条训练对在免费 A10 上能跑完两轮，成本为零。
  • 这条链跑通后，换 AutoDL 只是换环境，步骤一模一样。
一句话带走免费额度足够训一个 1.7B 分类器——挡在前面的从来不是算力，是数据和评测没准备好。

  4. 4

一句话带走免费额度的真实限制不是时长，是「一次性」——关掉再开，环境要从头装一遍。

结论一条 pip install 装好 ms-swift，装完先验 GPU 再验命令，两样都过才往下走。

进实例后点「打开 Notebook」，新建一个 Python 3 内核的 notebook。先确认卡是通的：

python -c "import torch; print(torch.__version__, torch.cuda.is_available())"

True 和 A10 两样对上，再装框架：

pip install ms-swift -U
swift --help
$ swift --help
usage: swift [-h] {sft,infer,export,web-ui,...} ...
装完 swift 命令找不到装了但提示 command not found，多半是装进了别的 Python 环境。用 python -m pip install ms-swift -U 重装，或 python -m swift --help 直接调模块——Notebook 里跑 ! 开头的命令行时尤其容易踩这个。
这一步的判据不是「装完了」，是「swift --help 能打出一屏用法」。打不出来就别往下走，后面每条命令都会连环失败。
  • 先验 GPU 再装框架，两样都过才继续。
  • swift 找不到命令 = 装错环境，用 python -m swift 兜底。
  • Notebook 里跑命令加 !，但 pip 建议用 %pip，避免装到别的内核。
一句话带走环境问题的判断标准永远是「命令能不能跑出一个结果」，不是「装的时候有没有报错」。

4准备数据

结论传 train.jsonl 和 val.jsonl 两个文件到持久化目录，ms-swift 原生吃 query/response，不用转格式。

本地跑一条命令先把数据备好：

# 在项目根目录执行，产出 data/cls/export/ 下的平台数据
python scripts/export_platform_data.py
$ python scripts/export_platform_data.py
导出完成
  ms_swift      train=18338  val=2292
  llamafactory  train=18338  val=2292
  test_eval     2292 条（只含 question / label）

魔搭只需要 ms_swift 那两个文件。每行长这样：

1data/cls/export/ms_swift/train.jsonlquery / response
# query
请判断以下法律问题应适用哪部法律。只输出法律名称，不要解释。

问题：小王是一家个人独资企业的投资人，他的企业已经解散，
但仍有未偿还的债务，他需要承担什么样的偿还责任？

# response
个人独资企业法
指令就两句任务 + 输出约束。指令越长，模型越爱在输出里补解释，评测时就不好对齐。
response 只有一个词标签本身，不是整句。整句会让每个候选的 token 数不一样，打分时没法公平比。

Notebook 左侧文件树进到 /mnt/workspace/，新建目录 cls，把两个文件拖进去。

传到 /tmp 等于白传/tmp 和 /root 都不是持久化目录，实例一关就没了，重开还得重传 6 MB。认准 /mnt/workspace/——那是持久化盘，下次开机还在。
只传 train 不传 val训练能跑，但你只能看训练 loss，看不到验证准确率——也就没法判断什么时候该停。分类任务尤其要 val：loss 还在降、验证准确率已经不动了，就是过拟合的开始。
  • ms-swift 原生吃 query/response，不需要转 alpaca。
  • 两个文件都要传：train 用来学，val 用来判断什么时候停。
  • 只传 /mnt/workspace/，其他目录关了实例就没了。
一句话带走数据准备只有两个动作：把答案挡在输入之外，把验证集留在训练集之外。

5一条命令起训

结论一条 swift sft 起训：QLoRA 4bit + LoRA r=16，两轮，约 1 小时。
swift sft \
  --model Qwen/Qwen3-1.7B \
  --tuner_type lora \
  --quant_method bnb --quant_bits 4 \
  --dataset /mnt/workspace/cls/train.jsonl \
  --val_dataset /mnt/workspace/cls/val.jsonl \
  --torch_dtype bfloat16 \
  --num_train_epochs 2 \
  --per_device_train_batch_size 8 \
  --gradient_accumulation_steps 2 \
  --learning_rate 2e-4 \
  --lora_rank 16 --lora_alpha 32 \
  --target_modules all-linear \
  --max_length 512 \
  --eval_steps 100 --save_steps 100 --save_total_limit 2 \
  --logging_steps 20 \
  --warmup_ratio 0.05 \
  --output_dir /mnt/workspace/output/cls_qwen3

每个参数为什么这么填

参数取值为什么
--tuner_type loralorams-swift 没有 qlora 这个选项，别去搜
--quant_bits 44配合 lora 才叫 QLoRA：量化基座 + 训低秩补丁
--max_length 512512问题最长 333 字，加指令与标签，512 都富余
--num_train_epochs 2250 类收敛快，1 轮常欠、3 轮易过拟合
batch 8 × accum 216有效 batch 16，24G 卡显存还剩一半
--learning_rate 2e-42e-4QLoRA 常用档；1e-4 偏慢，5e-4 容易抖
--val_datasetval.jsonl开了才会每 100 步打一次验证准确率
模型名为什么是 Qwen/Qwen3-1.7B 而不是 -InstructQwen3 的发布约定是：Qwen3-1.7B 本身就是后训练版（会听指令），基座版才叫 Qwen3-1.7B-Base。所以这里填 Qwen3-1.7B 就是你要的那个「会听指令」的模型，加 -Instruct 反而找不到。

跑起来长什么样

$ swift sft --model Qwen/Qwen3-1.7B ...
trainable params: ~20 M || all params: ~1.7 B || trainable%: ~1.2
{'loss': 3.4, 'learning_rate': 1.8e-05, 'epoch': 0.04}
{'loss': 1.8, 'learning_rate': 4.0e-05, 'epoch': 0.17}
{'loss': 0.9, 'learning_rate': 5.6e-05, 'epoch': 0.35}
{'eval_accuracy': 0.6, 'loss': 0.6, 'epoch': 0.52}
{'loss': 0.4, 'learning_rate': 3.2e-05, 'epoch': 1.10}
{'eval_accuracy': 0.8, 'loss': 0.3, 'epoch': 1.35}

这是形态示意，不是实测值——你的数一定和这不一样，看趋势，不看绝对值。

两个必须盯的数一是 trainable% 应在 1%~2% 之间（说明只训了补丁，基座没动）；二是 eval_accuracy 在涨——只要它还在涨，就不用急着停。
loss 不能和别的任务比这里起始 loss 约 3.4，因为 50 类里瞎猜的正确率只有 2%，理论起点接近 ln(50)≈3.9。生成任务的 loss 起点通常是 2.x。跨任务比 loss 大小毫无意义，只能和自己同一任务的起点比。
  • ms-swift 里 QLoRA = lora + quant_bits 4，没有单独的 qlora 选项。
  • --val_dataset 一定要给，它决定你能不能看见「该停了」。
  • loss 只看自己这条曲线的下降，跨任务比毫无意义。
一句话带走训练参数里真正需要你判断的只有三个：学多久（epoch）、一次看多少（batch）、学多快（学习率）。

6看 loss 拿 adapter

结论训完的产物只有几十 MB，从 checkpoint-* 里挑验证准确率最高那个带走。
/mnt/workspace/output/cls_qwen3/
└─ v0-20261118-153012/            # 一次运行的编号目录
   ├─ checkpoint-600/
   │  ├─ adapter_config.json      # LoRA 配置
   │  └─ adapter_model.safetensors # 补丁权重，约 40 MB
   ├─ checkpoint-800/
   └─ logging.jsonl               # 完整 loss 与 eval 记录

为什么是几十 MB 而不是 3 GB：训的只是 1.16% 的补丁参数，基座一个字节没改。

怎么选 checkpoint做法
看验证准确率在 logging.jsonl 里搜 eval_accuracy，挑最高的那个步数
没有 val 的时候取最后一个 checkpoint（本课不建议，等于蒙）
不确定就都留--save_total_limit 2 已经只留最近两个，不会撑爆盘
把整个输出目录打包下载目录里有 log、有多个 checkpoint、有优化器状态，动辄几百 MB。只 tar 你选中的那个 checkpoint-* 目录，几十 MB 就够了。
# 只打包选中的那个 checkpoint
cd /mnt/workspace/output/cls_qwen3
tar -czf cls_adapter.tar.gz v0-20261118-153012/checkpoint-800/
  • 适配器只有几十 MB，不带基座——这是 LoRA 最实用的地方。
  • 选 checkpoint 的判据是 eval_accuracy，不是最后一个。
  • 只打包选中的那一个目录，别整包下载。
一句话带走适配器小不是附赠的好处，是它「只改一小块」这个设计本身的必然结果。

7验它学会了

结论先跑 zero-shot 基线，再跑微调后，两个 accuracy 摆在一起才叫「学会了」。

先跑基线

不加载适配器，让原始 Qwen3 直接做同样的 50 选 1：

python scripts/eval_cls.py --no-adapter \
  --model Qwen/Qwen3-1.7B \
  --data /mnt/workspace/cls/test_eval.jsonl \
  --limit 200
$ python scripts/eval_cls.py --no-adapter --limit 200
评测集 200 条 · 标签 50 类 · 基座 Qwen/Qwen3-1.7B
模式：zero-shot 基线
  100/200  accuracy=0.4
  200/200  accuracy=0.4
==============================================
accuracy : ~0.4
macro-F1 : ~0.3
top-3    : ~0.6

这个数就是天花板之外的地板。没有它，后面那个 0.8 几的准确率说明不了任何事——你不知道它是模型强，还是任务本来就简单。

再跑微调后

python scripts/eval_cls.py \
  --model Qwen/Qwen3-1.7B \
  --adapter /mnt/workspace/output/cls_qwen3/v0-20261118-153012/checkpoint-800 \
  --data /mnt/workspace/cls/test_eval.jsonl
结果怎么读三次数字一起看：accuracy 涨了多少（主指标）、macro-F1 有没有同步涨（小类没被牺牲）、top-3 是不是已经很接近 accuracy（差得远说明模型在瞎猜边缘）。
指标基线微调后怎么读
accuracy自己填自己填主指标，50 选 1 整体对不对
macro-F1自己填自己填小类有没有被牺牲
top-3自己填自己填「差一点就对」的比例
推理时不关 thinking 会算错Qwen3 有思考模式。如果推理时开着它，模型会在给答案前先输出一段「用户问的是……应该属于……」，logprob 打分就全乱了。eval_cls.py 里已经固定 enable_thinking=False，你换成 swift infer 手测时也要记得关。

换一条小改动确认你真懂

把 --limit 200 改成 --limit 2292，看 ratio 变不变。如果 200 条和 2292 条差很多，说明 test 集里小类样本少，随机性大——这本身就是个该记住的结论。

  • 基线不是可选项，它是「微调有用」的唯一对照。
  • accuracy 看总分，macro-F1 看公平，top-3 看接近度。
  • Qwen3 的 thinking 模式必须关，否则打分全乱。
一句话带走评测不是跑一个准确率，是「先有基线、再看公平、最后能指到最差的那几类」。

8小结

结论这一课把分类链在免费云上跑通了：18,338 条数据、一条命令训练、两组可对比的准确率。
层这次动了什么没动的部分
数据层导出 train / val / test_eval 三份原始 Triplet 只读，一条没改
训练层QLoRA 4bit，两轮，max_length 512基座一字节没动，只存 40 MB 补丁
评测层候选打分 + 基线对照 + 三指标不建索引、不碰检索

三条边界，越过就要重做

  • 数据不到持久化盘实例一关全丢，下次开机白手起家。
  • 不传 val 就开训你只能看到 loss 在降，看不到它什么时候开始变傻。
  • 不跑基线就报提升只有「微调后 0.8 几」，没有基线垫底，这个数没有任何说服力。

三条自检

每一步都能单独验，不用等全跑完
① 数据wc -l 出来 18338 和 2292，head 出来字段是 query/response
② 训练日志里 trainable% 在 1%~2%，eval_accuracy 在往上涨
③ 评测基线 accuracy 明显低于微调后；差得不多说明任务太简单或数据泄漏
下一步这套流程换到 AutoDL 一模一样，差别只在「数据放哪、配置怎么给」。下一课把同一条链搬到按小时计费的机器上，顺便换成 LLaMA-Factory 的 yaml 写法。
  • 五步里四步是环境与数据，训练本身只有一条命令。
  • 免费额度的限制是「环境一次性」，所以要一次跑完。
  • 能证明学会的只有两个数：基线、微调后——缺一个都不算数。
带走换平台时真正要重做的只有三步：数据放哪、配置文件叫什么、命令开头是谁。任务本身一步没变。
