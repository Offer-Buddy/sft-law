3ms-swift 是什么

结论魔搭官方的微调框架。它把「拼对话模板、组 batch、量化基座、挂 LoRA、存补丁」这些手写活收进参数，你只需要说清三件事：用什么模型、喂什么数据、怎么练。

装完了不弄清它管什么，后面那条命令就是一串黑箱字符。先看它在链条里站的位置：

一个入口，五个动作

所有能力都收在 swift 这一条命令下，靠子命令分派。上一章 swift --help 报错，根子就在这里：它必须先知道你要调哪个动作。

子命令干什么本课用不用
swift sft监督微调，用「输入→输出」对喂模型用，第 5 章起训
swift infer加载训好的权重直接生成用，第 8 章手测
swift export合并 LoRA 到基座，或导出量化版可选，想交一个整模型时才用
swift eval框架自带的评测脚手架不用，本课用 eval_cls.py 候选打分
swift pt继续预训练，只学语言不学对话不用
swift rlhf 系列偏好对齐（dpo / kto / grpo 等）不用，先把 SFT 这层打稳
swift deploy / web-ui起 API 服务、开网页界面不用
为什么本课不用 swift eval框架自带评测面向生成任务，比的是「答得像不像参考答案」。我们这是 50 选 1 的分类，要比的是「选得对不对」，还得长度归一化、还要 top-3——正好是 eval_cls.py 干的事。评测口径不统一，两个数就没法比。

参数只有三类

几十个参数看着吓人，其实分三堆，各管一件事：

类别代表参数决定什么
模型--model / --template用哪个权重、按哪套对话格式拼 prompt
数据--dataset / --val_dataset学什么、拿什么判断该停
训练--tuner_type / --quant_bits / --learning_rate / --output_dir怎么练、补丁存到哪
--template 能把人卡住，而且不报错每个模型的对话格式不一样：谁说话、哪段是用户、哪段是助手，全靠一套模板拼。ms-swift 内置各家模板，一般能按模型名猜出来，猜不到才报「找不到 template」，这时显式写 --template qwen3。真正难查的是另一种：模板填错了不报错，只让 loss 降得特别慢。

QLoRA 在这框架里长什么样

ms-swift 没有 --qlora 这个选项，搜不到是正常的。三种练法靠参数组合表达：

练法关键参数显存
全参--tuner_type full20G+，24G 卡贴着悬崖
LoRA--tuner_type lora6~8G
QLoRA--tuner_type lora + --quant_method bnb + --quant_bits 45~7G，本课主线

一句话记法：QLoRA = LoRA 那几个参数，加上「把基座压成 4bit」的两个开关。

同一套参数，两种给法

命令行适合边试边改，yaml 适合存档复现。写出来是一回事：

命令行：一条命令
swift sft \
  --model Qwen/Qwen3-1.7B \
  --tuner_type lora \
  --quant_bits 4 \
  --dataset train.jsonl
yaml：一份文件
# cls.yaml
model: Qwen/Qwen3-1.7B
tuner_type: lora
quant_bits: 4
dataset: train.jsonl
# 起训：swift sft --config cls.yaml

参数少时命令行更快；一超过十个、或者要给别人复现，就转 yaml——改一个数不用翻 history。L07 那边 LLaMA-Factory 直接以 yaml 为主，先在这里见过，到那边就不陌生。

同类工具，不同生态：ms-swift 跟魔搭绑得紧（模型、数据、免费算力都在一个站里），LLaMA-Factory 社区更大、WebUI 更好用。要干的事一模一样，差别只在叫法：

三个数怎么来的：8:1:1 的比例逻辑

前面 wc -l 打出的 18338 / 2292 / 2292，是 22,922 条标注对按 8:1:1 切出来的。这是常见起点，不是拍脑袋——两头挤出来的：train 要尽量大，val/test 又要大到指标稳得住。

8:1:1 怎么定下来的
是常规吗
8:1:1、7:1:2、6:2:2 都是常见起点，没有公式能算出「最优比例」——它取决于你有多少数据、指标要多稳
train 为什么 80%
全量才 22,922 条，最小类只有 93 条。训练数据再砍，小类更学不动——本项目本来就嫌数据少
val/test 为什么各 10%
50 类评测要按类看召回：val 每类平均 46 条才够判断；test 2,292 条让 accuracy 的标准误约 0.6 个百分点。再少，小类就抖得没法看
为什么一次切三份
train / val / test 零重叠。不是「先定 train 再抠 val」——那样模型见过 val 的题，验证分数当场虚高
最小类的 test 只有 8 条公益事业捐赠法在 test 里就 8 条，错 1 条跳 12.5 个百分点。所以报小类准确率必须同时报「这一类有几条」，只报百分比等于没报——这也是必须看 macro-F1 的原因。
口径提醒：脚本实际是随机切，不是分层L00 第 4 章把切分描述成「按比例分层（stratified sampling）切」，但 build_cls_dataset.py 实际是固定随机种子（seed=42）打乱后按 10% / 10% 切，没有按类分层。所以小类在 val / test 里分到几条是随机结果——公益法 train 70 / val 15 / test 8 就是实跑出来的数，val 那 15 条不是刻意多留的。要看某类真实分布，直接读 label_stats.json 或数文件，别按 10% 自己估。
  • ms-swift 原生吃 query/response，不需要转 alpaca。
  • 三个文件都要传：train 用来学，val 用来判断什么时候停，test_eval 是验收考卷。
  • 只传 /mnt/workspace/，其他目录关了实例就没了。
一句话带走数据准备只有两个动作：把答案挡在输入之外，把验证集留在训练集之外。

5配置训练

结论一条 swift sft 起训：QLoRA 4bit + LoRA r=16，两轮共 2294 步，实测约 2 小时。
swift sft \
  --model Qwen/Qwen3-1.7B \
  --tuner_type lora \
  --quant_method bnb --quant_bits 4 \
  --dataset /mnt/workspace/cls/train.jsonl \
  --val_dataset /mnt/workspace/cls/val.jsonl \
  --torch_dtype bfloat16 \
  --num_train_epochs 2 \
  --per_device_train_batch_size 8 \
  --gradient_accumulation_steps 2 \
  --learning_rate 2e-4 \
  --lora_rank 16 --lora_alpha 32 \
  --target_modules all-linear \
  --max_length 512 \
  --eval_steps 100 --save_steps 1147 --save_total_limit 3 \
  --logging_steps 20 \
  --warmup_ratio 0.05 \
  --output_dir /mnt/workspace/output/cls_qwen3
这条命令为什么没有行内注释shell 里反斜杠续行的命令，中间插一行 # 会把后面所有参数一起吞掉，整条命令直接失效。所以它只能整块复制，逐行解释放在下面表里。要写注释就把它落成 shell 脚本，或者干脆换成 yaml（L07 那种写法每行都能挂注释）。

每个参数为什么这么填

按填错的后果排，不按命令里的先后顺序。红档填错要么白训、要么等于蒙着眼训（验证集），蓝档决定学成什么样，灰档只影响你看见什么、盘上留什么——赶时间至少把红档那几行读完。

档位参数取值为什么
核心--modelQwen3-1.7B不加 -Instruct：Qwen3 里不带后缀的就是会听指令的版本
核心--datasettrain.jsonl本地 jsonl，字段是 query/response，ms-swift 原生认这两个名字；传错路径启动就报找不到文件
核心--val_datasetval.jsonl不给它就没有 eval_loss，第 7 章那套判断全失效。这是唯一一个「不填也能训完、但等于没长眼睛」的核心项——训练照跑，你却看不见它学没学会，所以不能当蓝档放过
核心--learning_rate 2e-42e-4QLoRA 常用档；1e-4 偏慢，5e-4 容易抖。唯一一个能一票否决的超参数；日志里为什么不等于 2e-4，详见下面专节
核心batch 8 × accum 216有效 batch 16，24G 卡显存还剩一半；显存不够就先降 batch 再提 accum
核心--num_train_epochs 2250 类收敛快，1 轮常欠、3 轮易过拟合
核心--max_length 512512单条样本的 token 上限。官方默认 None（= 模型上限 32768），超长样本默认整条删掉——详见下面专节

模型名为什么是 Qwen/Qwen3-1.7B 而不是 -InstructQwen3 的发布约定是：Qwen3-1.7B 本身就是后训练版（会听指令），基座版才叫 Qwen3-1.7B-Base。所以这里填 Qwen3-1.7B 就是你要的那个「会听指令」的模型，加 -Instruct 反而找不到。

专讲 --max_length：它到底卡的是什么

这是参数表里最容易被当成「填个差不多数就行」的一项，其实它是红档。一句话：它规定一条样本转成 token 之后最长多少个，超了怎么处理由另一个参数决定。

三问三答
控制什么
单条样本 token 数的上限：指令 + 问题 + 答案拼起来，转成 token 后超过这个数，就按 truncation_strategy 处理。不是控制训练多少条，也不是控制输出多长（分类输出就一个词，由 max_new_tokens 管）。
默认值
官方是 None，意思是取模型的 max_model_len——Qwen3-1.7B 是 32768。不是 512，也不是 1024。表格对比里写的「1024 起」是同类任务的经验起点，不是这个框架的默认值。
为什么设 512
本项目问题实测最长 333 字，加指令几十 token、加一个部法名，512 装得下还不浪费。真正的原因不是「够用」，是「不设就按 32768 预留」——一条样本占三万多位置，batch 8 当场 OOM。
设小了的代价是静默丢样本官方 truncation_strategy 默认是 delete：超长样本整条删掉，不是把尾巴切掉。可选值还有 left（左侧裁）、right（右侧裁）、split（切成多条，仅预训练支持）。本项目标签在末尾，一旦用 right 裁掉尾巴，答案就没了——那条等于白标。所以别为了省显存盲目往下调，先看有没有样本被删。
怎么确认没设小训练日志里留意被丢弃/截断的样本数；或者直接跑一遍 tokenizer，把 18,338 条 query 转成 token 看长度分布。333 字是字符数，中文一字常占 1~2 个 token，真实 token 数比 333 大——但仍在 512 以内，这是选 512 而不是 256 的原因。

专讲 batch 8 × accum 2：为什么不一次塞 16 条

命令里这两行看着啰嗦，其实是一个决定的两半。这就是梯度累加（gradient accumulation）：想让梯度按 16 条样本算，但显存一次只装得下 8 条，于是拆成「一批 8 条、攒 2 次」。

三问三答
8 管什么
--per_device_train_batch_size 8：每次前向塞几条样本，直接决定显存峰值。24G 卡上 8 条 × 512 token 还有余量；一口气填 16 就 OOM。
2 管什么
--gradient_accumulation_steps 2：梯度先攒着不清零，攒够 2 批才更新一次参数。它不省计算量——两批的前向一次没少做，省下的只是同一时刻要装进显存的样本数。
16 是什么
有效 batch（total batch size）= 8 × 2 = 16。官方原文写明 CPT/SFT 中梯度累加等价于用更大的 batch_size，所以梯度一样稳；每轮步数也按它算：18338 ÷ 16 ≈ 1147。
官方默认值藏着一个坑per_device_train_batch_size 默认 1；gradient_accumulation_steps 默认不是 1，而是 None——框架会自动反推一个值，让 total batch size ≥ 16（total = per_device batch × accum × world_size）。所以什么都不填，框架也会替你凑到 16；本项目显式写 8 × 2，是为了把显存占用和步数握在自己手里，而不是让框架猜。
显存不够怎么调先降 per_device_train_batch_size（8→4），再把 gradient_accumulation_steps 提上去（2→4），有效 batch 仍是 16，结果基本不变、显存峰值减半。但 accum 也不是白送：拉到 8×8 这类极端值，每轮步数暴跌、单次异常样本影响一个更大的批量，而且改了有效 batch 就得回头看学习率——见后面「改 batch 不改学习率，等于换了实验」那条。

专讲 --learning_rate 2e-4：它干嘛用，日志里为什么不是它

这是红档里唯一能一票否决的超参数——模型、数据填错是跑不起来，学习率填错是跑得起来但根本学不会。先把最基本的问题说透：它到底干嘛用？

训练说到底，就是拿 17 亿个权重，一批一批数据地「往正确答案那边挪」。梯度算出「往哪挪、挪多陡」，但没告诉你「这一步迈多大」——学习率就是决定步子大小的那个小数。它不指路，只管迈多远。

把图里那一步拆开：某个权重现在是 0.31，反向传播算出的梯度是 +0.8（正号表示「往大走 loss 上升」，所以要减）。真按 0.8 减等于一步跨出去十万八千里；2e-4 把它压成 0.00016，权重从 0.31 挪到 0.30984——一次改动肉眼看不出来，可同样的动作重复 2294 步、所有权重一起挪，模型就训出来了。

公式里那个减号最让人犯嘀咕：为什么不是加？要回答它，得先说清 梯度（gradient）到底是什么。

梯度是什么——反向传播会给 17 亿个权重每个算一个数：「这个权重稍微加大一点，loss 会涨多少」。这 17 亿个数排成一列，就是梯度，一个和模型一样大的向量。它的正负号指方向：本例算出 +0.8，意思是「把 0.31 往上拨，罚分会涨」；绝对值 0.8 说的是坡有多陡。整体看，梯度永远指向 loss 上涨最快的方向——L00 第 4 章用「查账」的比喻讲过它怎么被算出来。

为什么是减法——我们要的是 loss 下降，可梯度偏偏指着上涨的方向，两者正好相反，所以公式必须取负：参数 ← 参数 − 学习率 × 梯度。拿数字走一遍：梯度 +0.8（上坡），乘学习率 2e-4 得步长 0.00016，再从 0.31 里减掉，落到 0.30984——权重变小，正是沿坡往下走了一小步。要是这个权重的梯度是 −0.8，减负数等于加，权重反而变大——不管哪种，都是朝 loss 更低的地方走。「下降」说的是 loss 在降，不是权重在降。

名字的来历「梯度下降」（gradient descent）四个字就是这么来的：梯度指上坡，取负反着走，loss 就一步步降下去。要是目标反过来要最大化——比如 RLHF（Reinforcement Learning from Human Feedback，人类反馈强化学习）训奖励模型，分数越高越好——就沿梯度正方向走、公式变加号，那叫「梯度上升」——用减号还是加号，取决于你要降还是要升。
别把这四个词混成一个反向传播负责算，梯度是算出来的结果（指向 loss 上升最快的方向），学习率只定步长，梯度下降是「照着挪」这个动作。学习率不指路，也不是梯度的一部分——L00 第 4 章有完整拆解。

弄清它干嘛用，再看那个新手必问的困惑：命令里填的是 2e-4，日志里打的却是 1.9e-05 这种数，是不是没生效？不是——你填的是峰值，日志打的是当前步的即时值，两个数是两种东西。

三问三答
它控制什么
只决定每次参数更新迈多远，不决定往哪走、更不管训几条训几轮——方向是梯度的正负定的（上面那张图把「一步更新」拆开了）。
2e-4 怎么读
科学计数法，就是 0.0002。官方默认：全参训练 1e-5、LoRA 这类 tuner 1e-4；本课是 QLoRA，取 LoRA 档偏上的 2e-4。别照抄全参的 2e-5——那是给「17 亿个参数全都动」用的，LoRA 只训旁边的小补丁，可以也该大一个量级。偏大（5e-4 往上）loss 抖甚至 nan，偏小两轮学不完；第 6 章「微调技巧」有五档对照表。
日志为什么不是 2e-4
因为日志打的是即时值：warmup_ratio 0.05 让它在前 115 步从 0 线性爬到 2e-4，之后默认 lr_scheduler_type cosine 再缓降回 0。所以开局看到 1.9e-05 是还在爬坡，不是配置丢了；判定生效要看它中段能不能爬到接近 2e-4。
别拿 L04 那段 demo 日志来对这个数L04「看 loss」里的 1.9e-05 → 6.0e-05 是 500 条小 demo 的示意记录，从来没爬到 2e-4，不是本课全量训练的结果。要看学习率调度对不对，看你自己这次运行的日志：起步小、中段接近 2e-4、末段回落，三段齐全才对。如果全程都停在 1e-5 量级不动，先查是不是把全参的配置抄了过来。
怎么判断这个数填对了把 loss 曲线和学习率曲线叠着看：loss 从接近 ln(50)≈3.9 一路降、中途不反弹，同时学习率走完「升—峰值—降」三段，就算对。loss 变成 nan 或突然弹回 3.x，先降学习率——这是它一票否决的另一种表现。

验证和保存：三组参数各管一件事

参数表里 --val_dataset、--eval_steps、--save_steps 挨着填，看着像一组，其实答的是三个不相干的问题：拿什么考、多久考一次、什么时候拍快照。这三样拆开，日志才看得懂。

记住验证集（validation set）必须是训练集之外的另一块数据。拿训练集自己验证，等于用做过的题当考试——模型见过答案，分数虚高，专测不出过拟合（overfitting）。

再看「多久」这一轴。--eval_steps 100 是每 100 步暂停一下，拿 val 的 2292 条跑一遍前向、打个分；--save_steps 1147 是每 1147 步把当时的权重拍一份检查点（checkpoint）存到盘上。评测只打分，存档才落盘——两件事。

把两个 step 设成同一个数（比如都填 200），为的就是分数和快照一一对上号：第 800 步打的 eval_loss 最低，对应的就是 checkpoint-800 那份权重。对不上号，后面想挑最优都无从挑起。

参数它管什么落盘吗
--val_dataset拿 val.jsonl 当考卷；不给就没有 eval_loss不落盘模型，只出分数
--eval_steps 100每 100 步考一次；不给就跟随 save_steps只在日志里留分数
--save_steps 1147每 1147 步拍一次权重快照落盘，这就是 checkpoint
--save_total_limit 3磁盘上最多留几份，超了删旧的只管删，不新增
load_best_model_at_end训完把分最高的那份摆回 output_dir不新增，只是摆回来
ms-swift 的对齐写法把保存和评测钉在同一个刻度，再让框架自己收尾：
swift sft \
  --val_dataset /mnt/workspace/cls/val.jsonl \
  --eval_strategy steps --eval_steps 200 \
  --save_strategy steps --save_steps 200 \
  --save_total_limit 3 \
  --metric_for_best_model loss \
  --create_checkpoint_symlink true
这里只列出要改的几行，其余参数照抄本章那条命令。注意最后一行不要带续行的反斜杠——后面接注释行会把参数一起吞掉（本章开头讲过）。官方参数表写明：eval_steps 默认跟随 save_steps、eval_strategy 默认跟随 save_strategy。所以本代码里的 eval_strategy 和 eval_steps 不写也能跑，写出来是为了让读配置的人一眼看到「在按步考」。
自动回最优挑的是 loss，不是准确率分类任务里 metric_for_best_model 填不了 accuracy——ms-swift 只认 loss、rouge-l、reward 这几种，默认就是 loss。你要的却是「50 选 1 选对率」。这两样不保证同向：loss 还在微降、验证选对率已经走平甚至回落，是这个规模上很常见的一段。真要按准确率挑，训完拿 val 逐个 checkpoint 扫一遍（第 7 章那套）。
load_best_model_at_end 先查再写官方命令行参数表没收录这个参数名，它是底层训练器认的字段，版本不同不一定能从命令行透传。更稳的是 --create_checkpoint_symlink true：官方说明它会额外建 output_dir/best 和 output_dir/last 两个软链接（symbolic link），要哪份指哪份，不依赖那个参数。另外 save_total_limit 的口径要对一下——官方参数表写「设 2 则保留 best 与 last」，本章前面和第 6 章都按「只留最近几个」讲，两处说法不一致；以你装的版本的 --help 为准，别把它当成「自动留最优」的保证。
test 看一眼就污染发现最终分数不理想，回头改学习率、改轮数、再跑一次看 test——这时 test 已经变成第二个验证集，报出来的数不再可信。要调参只看 val，test 留到最后一次性验收。

step 和 epoch 不是一回事

日志里同时出现 'epoch': 0.001 和 'global_step/max_steps': '1/2294'。这两个不是两套指标，是同一件事的两种刻度。

名词是什么在本课的数字
epoch把训练集完整过一遍叫一轮--num_train_epochs 2，即过两遍
step参数更新一次——攒够一个有效 batch 才更新一轮 1147 步，两轮 2294 步
batch一次塞进去几条样本8 条 × 攒 2 次 = 16 条更新一次

换算只有一句：每轮步数 = 训练集条数 ÷ 有效 batch，向上取整。本课刚好除不尽：

# 一轮多少步
18338 条 ÷ (8 × 2) = 1146.125  →  向上取整 1147 步
# 两轮合计
1147 × 2 = 2294 步   # 就是日志里 max_steps 那个数
账对得上，说明没算错日志首行 'epoch': 0.001 就是 1 ÷ 1147 ≈ 0.0009；到第 20 步是 20 ÷ 1147 = 0.01744，和你日志里的 0.0174444 一模一样。epoch 字段是进度（0 到 2 之间的小数），不是「第几轮」。

--num_train_epochs 一改，步数跟着改，时长也跟着改。三个数一起看才有意义：

轮数（epoch）步数大约多久（含验证，估算）
11147约 55 分钟
2（本课）2294约 2 小时
33441约 2 小时 50 分

耗时里训练只占三分之一，大头是那 20 多次验证——每次要在 2292 条 val 上跑一遍前向。所以步数翻倍不等于时间翻倍，但验证次数同样翻倍，时间还是接近翻倍。

所以「到底训多少 step」——答案是你从来没填过它。你填的是 --num_train_epochs 2，2294 是框架替你算出来的。

什么时候才需要手填 step只有三种：换数据集想固定预算、从某个 checkpoint 续训、或者短跑试水（--max_steps 100 十分钟看趋势）。正常训练一律填 epoch——它的含义是「把数据看几遍」，和样本数解耦，下次换数据集不用重算。
别拿「步数够不够」当判据2294 不是目标，是两轮的自然结果。够不够只看一件事：eval_loss 还在不在降。还在降就是没学够，走平或抬头就是该停。

global_step/max_steps，值形如 "100/2294"——分子就是 checkpoint-N 的 N
② 学没学会
trainable% 在 1%~2%（只训了补丁）+ eval_loss 还在降（还没学够）
③ 健康检查
eval_token_acc，只看它有没有崩——它 40 步就顶到 0.98，涨不动是常态

上面这些数是本课实测的，黄底就是你要盯的地方。有个坑先说：验证指标叫 eval_token_acc，不叫 eval_accuracy——按后者去搜，一行都搜不到。

token_acc 四十步就冲到 0.92，别被骗它是逐 token 的命中率。标签是「个人独资企业法」这种常用汉字串，模型本来就能猜中大半，所以这个数很快就顶到 0.98 左右，之后几乎不动——它对「50 个候选挑对一个」毫无区分度。真想知道选对率，得靠第 8 章那套候选打分。
loss 不能和别的任务比这里起始 loss 是 2.50，比「50 类瞎猜」该有的低得多。因为 loss 是逐 token 算的交叉熵，不是输出层直接做 50 分类——别拿 ln(50)≈3.9 去套。跨任务比 loss 大小毫无意义，只能和自己同一任务的起点比。
  • 一条 swift sft 起训：QLoRA = lora + quant_bits 4，ms-swift 没有单独的 qlora 选项。
  • --val_dataset 一定要给，它决定你能不能看见 eval_loss 的走向。
  • 步数不用手填：18338 ÷ 16 向上取整 = 1147 步一轮，两轮 2294 步。
  • 日志只盯三处：global_step/max_steps 看进度、eval_loss 看还在不在学、trainable% 看补丁挂上没有。
一句话带走训练参数里真正需要你判断的只有三个：学多久（epoch）、一次看多少（batch）、学多快（学习率）——其余都是这三样的衍生。

6微调常用技巧

结论命令只是骨架。真正决定这一版能不能强过上一版的，是下面这些手法：先试水、只改一个、算清验证的账、按判断存点。

这些手法和框架无关——换成下一课的 LLaMA-Factory、换成别的任务，做法一字不用改。

先定存点：四种存法，按训练长度选

顺序上先解决「留几个快照」，因为它决定你训完能不能比。存得太密、留得太少，等于什么都没留下。

存法怎么设适用
按轮存save_steps = 每轮步数，或 save_strategy=epochepoch 少（1~3 轮），想对比「第 1 轮 vs 第 2 轮」——本课用这个
按步对齐 evalsave_steps = eval_steps（如都设 200），save_total_limit 3，加 load_best_model_at_end最通用：训完自动把最优权重摆回 output_dir，磁盘也省
只在最后存save_strategy=no已经确定要训多少、只交一个产物；全参微调常见（一个 checkpoint 几十 GB）
按时间存save_steps 折算成约 30 分钟一步长训练（几小时以上），防断电崩溃白跑

共性是保存间隔要对齐你要做的判断：想比轮次就按轮存，想抓最优点就对齐 eval 并让框架自动回最优，什么都不想比就只在最后存一个。

起训要填的数不止保存这一组

保存间隔只管「留证据」。真正决定模型学成什么样的是另外八组数——超参数，就是你在命令里亲手填的那几个：学习率、轮数、batch 大小、LoRA 容量、验证频率。

它和模型里那 17 亿个「会被训练改」的权重不是一回事：权重是训出来的，超参数是你填进去的。八组按「改完之后影响什么」分成三堆。

LoRA 容量（r / α / 挂哪几层）16 / 32 / all-linear补丁能装多少东西。r 翻倍容量涨，显存与过拟合一起涨

超参数一：学习率，唯一能一票否决的

别的超参数填错，是「效果差一点」；学习率填错，是「根本学不会」或者「直接崩」。同一任务上五档的差别（中间一列是量级示意，不是逐档实测）：

学习率跑到 100 步时说明
5e-5loss 还在 1.8 上下不是学不动，是两轮根本学不完——全参微调才用这一档
1e-40.4 左右偏保守，模型大或数据多时用
2e-40.086QLoRA 的常用档，本课就取这个
5e-40.3 上下，还带锯齿步子太大，一步跨过谷底又弹回来
1e-3nan，或从 3.x 不再降直接崩，日志里 grad_norm 会先炸

--warmup_ratio 0.05 是前 5% 的步数把学习率从 0 线性升到 2e-4，2294 步里约 115 步。没有预热，第一步就可能用满 2e-4 把预训练权重推歪。

另一半是衰减：调度器按 cosine 到两轮末降回 0，末段步子越来越小，正好落在谷底而不是反复横跨。ms-swift 默认就是 cosine，不用显式写。

改 batch 不改学习率，等于换了实验有效 batch 从 16 提到 32，同一个 2e-4 相当于把步子放大一倍。要么按「学习率随 batch 线性放大」一起调（16→32，2e-4→4e-4），要么这次就别动 batch——否则结果不可比，你会把「换了 batch」的功劳记到别处。

超参数二：LoRA 容量，先别加 r

r=16、α=32、挂 all-linear，这三个数各自管什么：

参数取值管什么
lora_rank16补丁的宽度。越大能装越复杂的东西，也越容易背下训练集
lora_alpha32缩放系数。真正起作用的是 α ÷ r = 2 这个比例，惯例取 2
target_modulesall-linear补丁贴在哪。all-linear 连 MLP 一起贴，参数约是只贴 q/v 的两倍
lora_dropout0.05随机丢一部分输入防过拟合；数据上万条时作用很小

本任务的输出只有一部法名，四到八个 token。容量需求极低，r=16 已经富余——这里不是「越大越好」。

什么时候才该加 r只有三种：一是欠拟合，训练 loss 降不到 1 以下、验证也高；二是类数从 50 涨到几百；三是输出从「一个词」变成「一段理由」。本课一条都不占。

超参数三：验证比训练贵，eval_steps 最被低估

实测账很反直觉：训练 0.86 秒一步，一次验证要 208 到 286 秒。两者差两个数量级。

# 每 100 步的实际开销（本项目实测）
训练 100 步 × 0.86 秒 = 86 秒
验证 1 次（2292 条 val）≈ 236 秒
# 合计 322 秒，其中 73% 花在验证上

整轮算下来：训练 2294 步约 33 分钟，二十多次验证约 90 分钟。「两小时训练」里有九十分钟在看考卷，不是在学。

改法怎么设换到什么
拉长间隔eval_steps 100 → 200验证次数减半、省约 45 分钟；曲线粗一半，仍能看出走平没有
缩小验证集另存 300 条 val_small 做过程监控，全量只在轮末跑每次 236 秒降到约 31 秒，省一个多小时；代价是中途的数抖动更大
只在轮末验eval_steps = 每轮步数全程只验 2 次，最省；但中间两个半小时是黑箱
不动每 100 步一次换来 23 个观测点，能看清拐点——本课选这个，因为总共只有两小时预算
唯一不能做的是「干脆不给 val」省下九十分钟，代价是连 eval_loss 都没有——第 7 章那套「看曲线判断该不该停」全部失效，只能取最后一个 checkpoint，等于蒙。

三件现在别动的事

正则化（weight_decay / dropout）只训 1.2% 参数，这两样几乎不起作用。真过拟合就减轮数——这是本规模下唯一有效的主开关，调正则只是自我安慰。
类别重采样、class weight会改掉「真实分布」这个先验，而你的验收尺子是 macro-F1——重采样之后这把尺子本身就失真了。不均衡先看混淆矩阵，别急着动数据。
packing（多条短样本拼成一条）能提速两三倍，但会让 loss 在样本之间串味，算出来的数和你逐条推理时不是一回事。先跑通，再谈快。

还有一条最难守的：一次只改一个超参数。同时改学习率和 batch，结果变好了你也不知道是谁的功劳——这就是「调参两小时，不如重跑二十分钟」的由来。

七条技巧一张表

把上面这些手法收成一张表：能搬到下一个任务上的共七条。前四条决定模型学成什么样，后三条决定你要花多少时间和磁盘。

技巧怎么做什么时候拿出来
先试水再长跑原命令末尾加 --max_steps 100 和临时的 --output_dir .../smoke，只看三件事：loss 动没动、显存超没超、产物在不在任何超过半小时的训练之前。两分钟换一次不赌
一次只改一个超参数这一版只改学习率，其余照抄上一版；同时改两个，等于重开一次实验永远。这是「调参两小时不如重跑二十分钟」的由来
学习率配预热与衰减QLoRA 取 2e-4，warmup_ratio 0.05 线性升温，末段由 cosine 降回 0每次起训都要。唯一能一票否决的参数，别的错了是差一点，它错了是学不会
容量够用就停--lora_rank 16、--lora_alpha 32、挂 all-linear；想提升先加数据、改轮数，不动 r欠拟合、类数暴涨、输出从词变成段之前，r 一律不动
把验证的账算清拉长 --eval_steps、抽 300 条小验证集做过程监控、或只在轮末验；--val_dataset 必给验证吃掉大半训练时间时——本课两小时里九十分钟在看考卷
存点对着判断设比轮次就按轮存；抓最优点就 save_steps 对齐 eval_steps 加 load_best_model_at_end；只交一个就 save_strategy no先想清楚「训完要比什么」，再回头定 --save_steps
过拟合先减轮数--num_train_epochs 降一档重训；dropout、weight decay、重采样都不是这个规模的第一手段eval_loss 连抬三次且累计过 0.01，才算真过拟合
  • 七条分两半：前四条改结果，后三条改成本与判断——只有「一次只改一个」，结论才可比。
  • 八组超参数归三堆：改结果、改成本、改判断；混着改，变好变坏都说不清是谁干的。
  • 验证比训练贵七倍，eval_steps 是最该算的账；但省它的唯一禁招是「干脆不给 val」。
  • loss 只能和自己这条曲线比，跨任务比毫无意义；真想知道选对率，得回 test 集跑一次。
一句话带走技巧的价值不在多，在于每一条都替你挡住一次「白跑两小时」：先试水、只动一个、算清验证的账、按判断存点。

不用逐个目录进去翻分数不在目录里——logging.jsonl 一条不落记全了，目录名 checkpoint-N 的 N 就是日志里的 step。ls -d checkpoint-* 出来和表一对即可，选中哪个才 cd 进去打包。
嫌一轮太粗，就按半轮存把 --save_steps 改成 573（半轮）、--save_total_limit 提到 5，就能拿到 573 / 1147 / 1720 / 2294 四个点，拐点看得更细，代价是每多一个 40 MB。但别退回 100 步一存：那样 limit 只留最近两个，刚好把有意义的对比全删光。
  • 适配器只有几十 MB，不带基座——这是 LoRA 最实用的地方。
  • 日志报的是 token 级准确率，不是 50 选 1 的选对率；判断还能不能学看 eval_loss。
  • checkpoint-N 的 N 就是日志里的 step，两边对上才拿得对。
  • 存 checkpoint 要跨轮次：一轮一个才有对比价值，相邻两个快照比了等于没比。
一句话带走适配器小不是附赠的好处，是它「只改一小块」这个设计本身的必然结果。

8验它学会了

结论先跑 zero-shot 基线，再跑微调后，两个 accuracy 摆在一起才叫「学会了」。

进这一章先回答一个高频疑问：评测还要再装一套工具吗？不用。训练和验收就在同一台魔搭实例上，装一次 ms-swift，评测脚本要的底层库全都跟着进来了——你直接 python scripts/eval_cls.py 就能跑。

图里那个 peft 是什么两层意思别混：大写 PEFT（Parameter-Efficient Fine-Tuning，参数高效微调）是一类方法的统称——冻结原权重、只训旁挂的一小块，LoRA 就是其中最常用的做法；小写 peft 是 HuggingFace 出的 Python 库，专门实现这类方法。脚本里 from peft import PeftModel 做的就是「把训好的 LoRA 小矩阵挂回基座」，也就是所谓「python 挂载」，不用自己写低秩矩阵怎么乘、怎么加。
别自己升级底层库ms-swift 官方锁了 transformers>=4.33,<5.23.0、peft>=0.11,<0.21——再跑 pip install transformers -U 可能把版本顶出兼容范围，ms-swift 和评测脚本一起坏。装 ms-swift 时装进来的版本就是配套版本，直接用。「不用额外装」只在魔搭这台实例上成立，换到本地或创空间就得照脚本报错提示装 torch transformers peft accelerate。

脚本里在干嘛：五步走到 accuracy

上面两条命令一路跑到底，输出的 accuracy 到底怎么算出来的？值得逐段看一遍——它是把「50 选 1」从生成题改造成了打分题，这是整套评测最该懂的一处，也是它跟「让模型自由生成再对答案」最不一样的地方。

先拆第 ③ 步：为什么要「造 prompt」

「造 prompt」听着像提示工程，其实跟「提示模型好好回答」没关系。它是把问题包回训练时的形状——训练时 ms-swift 用 qwen3 对话模板把每条 query 包成带角色标记的文本，模型学的是「看到这个形状 → 输出部法名」；评测若把问题裸着喂进去，模型看到的是它从没见过的形状，分数会掉得莫名其妙。

# 脚本第 63–66 行：把问题包成训练时的对话形状
messages = [{"role": "user", "content": f"{instruction}\n\n问题：{question}"}]
tokenizer.apply_chat_template(messages, enable_thinking=False, add_generation_prompt=True)
prefix 的两个作用，一个都不能少
形态对齐
训练时见过 <|im_start|>user … <|im_end|> 这个形状，评测用同一个模板包，模型才认得出「这是要分类的问题」，不是没头没尾的裸文本
定位锚点
add_generation_prompt=True 在末尾补上 <|im_start|>assistant，等于插一根标杆说「用户说完了，从这里开始输出部法名」——候选打分就是接着它算的
那个 offset = len(prefix) − 1 也从这来logits 比输入错一位（它预测的是下一个 token），减 1 才能对准候选的第一个字。没有 prefix，连「从哪一格开始算」这个坐标都不存在——所以造 prompt 和候选打分是同一件事的两半。
关思考为什么塞在同一步Qwen3 是混合思考模型，模板默认可能让它先吐一段「用户问的是……」。一旦 prefix 后面跟的是推理文本而不是部法名，候选的打分位置全乱。所以第 66 行显式写 enable_thinking=False（老版本 tokenizer 不认这个参数，下面几行用 try/except 兜底）。

核心：候选打分，不问它「生成什么」

看这段（批处理细节先不展开）。50 个部法名先各自转成 token，拼成一个大批次，一次前向把分数全算出来——比逐个跑快约 50 倍：

# 1. 50 个候选拼成 batch，一次前向拿到全部位置的对数概率
seqs   = [prefix + label_ids[lab] + [eos] for lab in labels]
logits = model(input_ids=batch).logits
logp   = torch.log_softmax(logits, dim=-1)

# 2. 每个候选：把它那些 token 的 logprob 加起来，再除以 token 数
for lab, ids in label_ids.items():
    s = sum(logp[i, offset+j, tid] for j, tid in enumerate(ids))
    scores[lab] = s / len(ids)      # ← 长度归一化

pred = max(scores, key=scores.get)   # 3. 取最高分那个部法名
三个设计，一个都不能少
算概率
不让它自由生成，答案就天然落在 50 类之内——不会冒出「民法典合同编」这种标签外的名字，也没法靠措辞运气蒙对
除以长度
logprob 是负数、越加越小。不归一化的话，「个人独资企业法」6 个字就比「合同法」3 个字系统性吃亏——取平均才公平
算进 eos
让模型为「说到这里结束」也打个分，避免它偏爱那些没说完就截断的短名字
隐藏坑
offset = len(prefix) − 1：logits 比输入错一位（预测的是下一个 token），不减 1 就对不上候选的第一个字，分数全乱

accuracy 是个什么数：答对几题 ÷ 一共几题

报告第一行的 accuracy（准确率）最该看懂——它就是考试做对了几成：答对的题数 ÷ 总题数。模型对 test 的 2,292 道题各吐一个部法名，和标准答案逐一比对，如下：

但这个数会骗人——这是本项目反复强调的一点accuracy 把 50 类混在一起算总分，大类题多、小类题少，于是「全押大类」也能刷出不错的分数。你的项目里类别差 40 倍：民法典 3,727 条，公益事业捐赠法只有 93 条。模型要是把小类全猜成民法典，大类那边的 accuracy 照样好看，可小类一个没对——总分把它掩盖了。

所以 accuracy 只当主指标，必须配着下面三个一起看：

指标回答什么
accuracy50 选 1 整体对了多少（会被大类带偏）
macro-F1每一类平均好不好，小类错了立刻掉——最公平
top-3正确答案进前三就算命中，看模型「离对有多远」
混淆矩阵哪两类老互相认错，直接指到病灶
最小类的抖动尤其要看公益事业捐赠法在 test 里只有 8 条，错 1 条就是 12.5 个百分点——光报一个 accuracy 根本看不出这种抖动，这也是为什么必须同时看 macro-F1。
指标怎么读accuracy 是主指标——选对几条除以总数；macro-F1 是 50 个类各自算 F1 再取平均，大类小类同权，防「全猜大类也得高分」；top-3 是正确答案进前三就算命中，看模型离对有多远。报告还会输出 F1 最差的 5 类和完整混淆矩阵，供下一章查「哪两类老认错」。
线上线下必须是同一把尺子候选打分的三处口径——模板与思考开关、候选集含 eos、长度归一化——部署上线时一处都不能改。部署那一课的「三处必须同口径」说的就是这里：改一处，报告上的 accuracy 就不作数了。

两个都不错时，怎么定一个

「谁高留谁」在差 5 个百分点时成立，在差 0.3 个百分点时不成立——那不是模型差别，是抽样噪声。

2292 条测试集，能分辨多大的差别
标准误
accuracy 0.9 附近时 √(0.9 × 0.1 ÷ 2292) ≈ 0.6 个百分点
95% 区间
约 ±1.2 个百分点——比这更小的差，换个随机种子就反过来了
两个 checkpoint 差多少说明什么选哪个
> 2 个百分点真差别取高的，并在报告里写明
1 ~ 2 个百分点可能有差别，也可能没有取高的，注明「差异接近误差边界」
< 1 个百分点就是噪声，换个种子会翻取步数小的（checkpoint-1147）：训得更少，过拟合风险更低
两个都比基线高不到 10 个点不是挑的问题训练没成，回去查数据格式与学习率

所以选的意义不在「挑出冠军」，而在知道该训几轮：2294 明显低于 1147，说明第 2 轮确实在学；两者打平，说明第 2 轮白训、下次一轮就够——这一条比分数本身有用。

严谨做法：val 上挑，test 上报在 test 集上反复比、挑最高的那个报，分数会带「事后择优」的水分。规范是：val 集挑 checkpoint，test 集只在最后跑一次报最终成绩。val 是 query/response 格式，转一下就能喂给评测脚本：
# 把 val 转成考卷格式，结果写进 val_eval.jsonl，原文件不动
# 只做两件事：query 剥成纯问题、response 改名 label
python - <<'PY' > /mnt/workspace/cls/val_eval.jsonl
import json
for l in open('/mnt/workspace/cls/val.jsonl'):
    if not l.strip():        # 空行会让 json.loads 直接抛错
        continue
    r = json.loads(l)
    # 训练数据的 query 自带指令前缀，评测脚本会再拼一次，先剥掉
    q = r['query'].split('\n\n问题：', 1)[-1]

然后 --data 指 val_eval.jsonl，两个 checkpoint 各跑一次，挑高的那个；最后把 --data 换成 test_eval.jsonl 只跑一次，那个数才是能写进报告的。

定下之后只做三件事：只打包这一个目录、把 checkpoint-N 写进实验记录、把它当作 v1 存档。以后每改一版都拿 v1 对比，不然「改好了」永远只是感觉。

结果怎么读三次数字一起看：accuracy 涨了多少（主指标）、macro-F1 有没有同步涨（小类没被牺牲）、top-3 是不是已经很接近 accuracy（差得远说明模型在瞎猜边缘）。
指标基线微调后怎么读
accuracy自己填自己填主指标，50 选 1 整体对不对
macro-F1自己填自己填小类有没有被牺牲
top-3自己填自己填「差一点就对」的比例

一次训练算不算成，看四层

只看最后的 accuracy，只能回答「考了多少分」，回答不了「该不该这么做」。四层依次过关，成果才站得住。

层看什么过关标准
① 跑对了trainable% 在 1%~2%、loss 从 2.5 降到 0.1 以下、没有 NaN训练确实发生了，不是空转
② 比原来强test accuracy 对比 zero-shot 基线差出几十个点（基线 0.4 左右，微调后应在 0.8 以上）
③ 强得均衡macro-F1 与 accuracy 的差距、top-3、最小类召回两个指标差 5 个点以内；最小类召回不为 0
④ 错得可解释混淆矩阵里错在哪几类错在相邻部法可接受；错到无关的法上，说明没学会

第 ① 层只证明「训练没崩」，第 ② 层才是「微调有用」，第 ③ 层决定敢不敢用在小类上，第 ④ 层决定错误代价能不能接受。任何一层不过，后面的数都不用看。

最容易被低估的是最小类train 里只有 70 条的类（如公益事业捐赠法），整体 accuracy 再高也可能全错——它被 3,727 条的民法典淹了。所以必须单独看每类召回，macro-F1 就是为这件事存在的。

两种走不通的情况

上面那套判据有个前提：盘上这两个里至少有一个是好的。两种情况会让前提不成立。

一、两个都过拟合。先确认真假：eval_loss 连续三次以上单调抬升、幅度超过 0.01，同时训练 loss 还在往下走，这才是过拟合。

0.0112 抬到 0.0117（差 0.0005），那是噪声，不叫过拟合。

真的都过拟合，正解只有一个：把轮数降下来重训，--num_train_epochs 1。这个规模下轮数就是主开关，别指望加 dropout、调 weight decay 去救。

二、最好的那步没存下来。先怀疑这个判断：日志里 eval_loss 在小数第三位抖动，靠它定位「最优步」本来就不可靠。真明显低谷才可信——比如 1200 步 0.008、前后都是 0.02。

别指望 save 帮你记住最优步按轮存只管「轮末」。低谷如果落在 600 步这种轮中位置，压根没存过——不是被删，是没拍。想覆盖轮中，就把 --save_steps 设成半轮（573）并给足 --save_total_limit。真要锁定某个点，更省的办法是让终点落在那里：低点在 600 步就加 --max_steps 600。

一句话：epoch 决定终点，limit 只决定留几个尾巴。想控制停在哪，调前者；想多留几个候选，调后者。

推理时不关 thinking 会算错Qwen3 有思考模式。如果推理时开着它，模型会在给答案前先输出一段「用户问的是……应该属于……」，logprob 打分就全乱了。eval_cls.py 里已经固定 enable_thinking=False，你换成 swift infer 手测时也要记得关。

换一条小改动确认你真懂

把 --limit 200 改成 --limit 2292，看 ratio 变不变。如果 200 条和 2292 条差很多，说明 test 集里小类样本少，随机性大——这本身就是个该记住的结论。

  • 基线不是可选项，它是「微调有用」的唯一对照。
  • accuracy 看总分，macro-F1 看公平，top-3 看接近度。
  • 两个 checkpoint 各测一次；差 1 个百分点以内算打平，取步数少的那个。
  • Qwen3 的 thinking 模式必须关，否则打分全乱。
一句话带走评测不是跑一个准确率，是「先有基线、再看公平、最后能指到最差的那几类」。
