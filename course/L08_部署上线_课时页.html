1概述

结论训练只交出一个 40 MB 补丁；这一课把它变成「发一句话、回一个部法名」的服务，再交一页别人照着能接上的文档。

前七课一直在解决「让模型学会」。这一课换个问题：怎么让别人用上。两者中间隔着一个服务。

段做什么交付物怎么算过
① 打包 · 第 3 章整理补丁、标签、模板、版本号一个能直接挂上去的目录vllm serve 起得来
② 起服务 · 第 3 章挂 adapter，开 OpenAI 兼容接口一个 URL + 一个模型名curl /v1/models 看得到
③ 测一轮 · 第 4 章对齐口径、抽 200 条回测、压 P95一份对齐报告 + 一组延迟与离线差 ≤ 0.5 个点
④ 交接 · 第 5 章写文档、定回滚方式一页接入文档换个人照着能接上
本课不教什么K8s 编排、网关鉴权、Prometheus 监控栈、多卡张量并行——这些是运维层的活。本课只留一条判据：服务挂了能不能一分钟回到上一版。做不到就先别上生产，别的都可以后补。
  • 上线分四段：打包、起服务、测一轮、交接，每段有独立交付物。
  • 训练产出的是补丁，不是「一个模型」——基座（base model）谁都能拉，补丁只有你有。
  • 运维级能力挡在边界外，只留「一分钟回滚」这一条。
一句话带走上线不是把模型挂上网，是把「谁在调、调什么、出错怎么办」三件事写清楚——写不清就还没上线。

2选择引擎

结论用 vLLM，判据三条：挂得了 adapter、扛得住并发、给得出候选位置的对数概率（logprob）。引擎定了再定放哪——那一步由「数据能不能出内网」一票否决。
引擎现状（2026-11）挂 adapter给候选 logprob结论
vLLM v0.32.0生产级，OpenAI 兼容多 LoRA 同进程切换prompt_logprobs本课用它
SGLang v0.5.23前缀共享更强支持 LoRA serving支持长前缀场景更省，本课不展开
LLaMA-Factory api一条命令就起支持弱自测够用，扛不住并发
Ollama 0.34.1+本地最省事已移除不支持要用它得先合并成 GGUF
网上教程还停在旧版本Ollama 从 0.34.1（2026-09-15）起删掉了 ADAPTER，Modelfile 里写那一行会直接报错。你现在搜到的「两行搞定 LoRA」全是旧的：
Error: LoRA adapters are no longer supported

引擎选定了，再定放哪——它决定你能不能 7×24：

放哪适合计费本课
AutoDL 实例演示、短时验证按小时，关机就停用它跑通
阿里云 GPU 服务器7×24 对外服务按月生产常态
内网服务器数据不许出内网一次性采购法律场景很常见
云端托管不想碰运维按词元计费拿不到候选打分，本课不走

这张表里只有两家是「租卡」：AutoDL 按小时租，阿里云按月租——区别在租多久，不在机器本身。

魔搭（ModelScope）不租卡，它送一份免费额度：A10 24G 共 36 小时，绑阿里云账号才能开，用完就没了，不是每月刷新。

而且魔搭那份免费算力的底层就是阿里云——同一批机器，一个是白嫖入口，一个是花钱租。所以三家其实只有两套卡：AutoDL 一套，阿里云一套，魔搭是阿里云的免费马甲。

最后一行是另一条路：把训练数据传上去，平台帮你训，只给你一个 API 地址。省掉运维和显卡。

代价是补丁不在你手里，而且多数平台只返回生成结果、不返回候选位置的 logprob——这套 50 选 1 就打不了分。

三句话定部署位置
数据问题能不能出内网？不能就只能自建，云端托管直接出局
时长要 7×24 挂着的，按小时计费的机器不划算，包月或自购
并发同时问的人多不多？决定一张卡还是两张，先压一轮再决定
为什么不直接用 LLaMA-Factory 的 api它没有连续批处理：10 个人同时问，第 10 个要等前面 9 个算完。自测无感，对外就是「这系统好慢」。
  • 选引擎看三条：挂 adapter、并发、给不给 logprob，不看排名。
  • 「放哪」先于「用什么」：数据能不能出内网，一票否决。
  • Ollama 那条路 2026-09 已断，旧教程会把你带沟里；要它先合并成 GGUF。
一句话带走选型不是挑最强，是挑「这个任务要的三件事它都有」——三件事里缺一件，其他优点都不算数。

3打包发布

结论打包发布两步走：把补丁整理成一个能直接挂的目录，再一条命令挂上去。文档和回滚等压完测再写——没有数据，写出来也是空的。

只交补丁

挂 adapter，不合并。合并只在两种情况下做：要转 GGUF，或者要交一个能离线拷走的整包。

挂和合并的差别不在技术，在以后改起来疼不疼：

挂载（本课）
基座 3.4 GB（公共，谁都能拉） 补丁 40 MB（你的） 换版本 = 改一个名字 回滚 = 改回去 同时挂 v1 / v2 做灰度
前提：推理引擎（inference engine）支持 LoRA。
合并（少数情况才做）
整包 3.4 GB / 版本 换版本 = 传一份新的 回滚 = 留两份，6.8 GB 灰度要起两个进程
好处：兼容任何只认整模型的运行时。

一个能直接挂的目录长这样——基座不进包，只用一行字记着它是谁：

cls_adapter/                    # 从 checkpoint（training snapshot）-2294 拷出来的补丁
├── adapter_config.json        # 里面写着 r=16 和基座路径
└── adapter_model.safetensors  # 约 40 MB

service/                       # 服务侧要跟着走的两个文件
├── label_stats.json           # 50 个候选与样本数，顺序同 eval_cls.py
└── VERSION                    # cls-qwen3-1.7b-v1

这里先拆一个常被问混的：checkpoint 目录本身就是 adapter。LoRA 训练存的每个 checkpoint-N，里面装的就是上面那两个文件。

所以「打包」只有三步：挑一个、拷出来、改个名字——没有格式转换。

打包在你自己的电脑上做吗？不做。三步全在训练那台服务器上：cp -r checkpoint-574 cls_adapter 是服务器上的原地拷贝，补丁跟着服务走、不跟着你走。自己的笔记本从头到尾不参与——它没 GPU，也不跑服务。只有要转 GGUF、离线归档、或搬到另一台机器部署，才谈得上「下载到本地」。

指令那句不在文件里，写在 serve_cls.py 的 PROMPT 常量上——必须和训练时一字不差。改它等于换尺子，改完要重跑 test。

挑哪个：看 val，不看「最后一个」目录里有几个 checkpoint，就拿 val 逐个跑候选打分，谁高取谁。别默认取最后那个——过拟合（overfitting）的典型长相就是「越训越差」。

一个个手点太慢，扫一遍交给脚本。前提是 save_steps 调细到 287（1/8 轮）、不限 save_total_limit——L07 那份配置一轮只存一个点，扫不出峰。

脚本只加载一次基座，后面全是换 adapter 权重：

python scripts/sweep_checkpoints.py --dir /root/autodl-tmp/saves/qwen3-1.7b/cls --limit 300

# --limit 300：val 抽 300 条粗筛，固定 seed，几次跑的是同一批
# --limit 0  ：全量 val，粗筛出前两名后再比一次
checkpoint-287      acc=0.8067
checkpoint-574      acc=0.8412  ← 最佳
checkpoint-861      acc=0.8267
checkpoint-1148     acc=0.8133
checkpoint-1435     acc=0.7967
# 形态示意，你的数不会一样；要看的是峰落在哪一段

峰落在中间，是过拟合前的正常位置，取它。落在最后一个说明还没学够，加一轮再扫；落在第一个是学过头了，往更早的快照找。

300 条上的差距经常是噪声，粗筛出的前两名要拿全量 val 再比一次才作数。

save_total_limit 留的是「最近几个」，不是「最好的几个」它只会删最旧的，不知道谁最好。设成 3、又每 287 步存一份，八个点里前五个当场被删——峰要是在那儿，你永远看不见。
test 集只跑一次先在 test 上比、挑最高的那个报，数字会自带「事后择优」的水分。规范是 val 挑 checkpoint、test 只报最终成绩。
打包完先看两个字段adapter_config.json 里的 r 决定 --max-lora-rank 填多少；base_model_name_or_path 决定 vllm serve 后面跟哪个基座。这两个值填错，服务起不来或算出来的分数全不对。

还有一个反直觉的点：训练时用 4bit 量化，部署时不用。

阶段权重怎么存权重占用为什么
训练 · QLoRA（Quantized LoRA，4bit）基座 4bit + 补丁 bf16约 0.9 GB省显存，能在一张卡上塞下更大的模型
部署（本课）基座 bf16 + 补丁约 3.4 GB1.7B 本来就不大，没必要为省 2 GB 牺牲精度

这两列只比权重本身。训练还要加激活和优化器，部署还要留 KV cache（键值缓存）——真实显存都比这行数字大。

量化是训练时的省显存手段，不是交付格式。模型大到一张卡装不下时，才轮到部署侧量化。

版本号写在哪写在目录名和 VERSION 里，别只记在自己脑子里。回滚的时候你要能一眼看出「现在跑的是哪一版、上一版叫什么」——这一点比多写十行代码重要。

起个服务

一条 vllm serve，--enable-lora 把补丁挂上去；请求里 model 填适配器名，不是基座名。

在哪台机器上装就在训练那台 AutoDL 上装。--lora-modules cls=./cls_adapter 用的是本机路径，补丁在 /root/autodl-tmp，换台机器就得把补丁和基座都搬过去。魔搭也能装（有 root、能 pip），但它 36 小时是练手额度、闲置自动关，挂常驻服务会断——要 7×24 就换阿里云按月租的机器。
# 1) 装引擎（在有 GPU 的 Linux 机器上，版本以官网为准）
#    另开一个 conda 环境装，别污染训练环境
pip install -U vllm

# 2) 起服务：基座 + 补丁，一个进程
vllm serve Qwen/Qwen3-1.7B \
  --served-model-name cls-base \
  --enable-lora \
  --lora-modules cls=./cls_adapter \
  --max-lora-rank 16 \
  --max-loras 2 \
  --max-model-len 1024 \
  --gpu-memory-utilization 0.85 \
  --port 8000
$ vllm serve Qwen/Qwen3-1.7B ...
INFO Loading model weights took 3.42 GiB
INFO LoRA adapter 'cls' loaded from ./cls_adapter
INFO Starting vLLM API server on http://0.0.0.0:8000
基座名写错，服务起不来Qwen3 换了命名：后训练版不带后缀，Qwen/Qwen3-1.7B 就是指令版，基座才叫 -Base。Qwen2.5 时代那个 -Instruct 在这里不存在，写上去 vllm serve 直接报找不到仓库。

参数不少，真的会出问题的只有四个：

参数管什么写错的后果
--served-model-name基座在 API 里叫什么请求里名字对不上就 404
--lora-modules cls=路径挂一个叫 cls 的补丁路径错，服务直接起不来
--max-lora-rank允许的补丁宽度上限小于训练时的 r=16，加载失败
--max-model-len上下文上限开太大白占显存，容易 OOM
自检：两个名字都得在 
curl -s localhost:8000/v1/models | python -m json.tool
返回的 data 里应该同时有 cls-base（基座）和 cls（补丁）。只有前者说明 LoRA 没挂上，你的请求会打到没训过的基座上——分数会难看得莫名其妙。
三个最常见的翻车① CUDA out of memory：把 --gpu-memory-utilization 降到 0.8、--max-model-len 降到 512 再起；② max_lora_rank 报错（就是 --max-lora-rank）：填成训练时的 r（本课 16）；③ 404：请求里 model 写了基座名，或补丁名拼错。
再加一个补丁就是灰度--lora-modules cls=./v1 cls_new=./v2 就挂了两个；--max-loras 2 让它们在同一个 batch 里共存（设 1 会来回换入换出，慢）。调用方把 model 从 cls 改成 cls_new 就切过去了——回滚就是把名字改回来，不用重启。

三种上线组合

训练在哪、服务在哪，一共就三种真实组合。判据只有一条：补丁和服务必须在同一台机器——不同台，就得搬补丁。

组合跨机器要做的事怎么对外
AutoDL 训 → AutoDL 发不跨补丁原地，装引擎起服务，最省事控制台端口映射
AutoDL 训 → 阿里云发跨搬补丁到阿里云，基座重下，改路径，重验口径公网 IP + 安全组
魔搭训 → 阿里云发跨同上；只是源端取补丁更绕（魔搭无原生 SSH）公网 IP + 安全组

第一条不用多说：补丁就在 /root/autodl-tmp，装 vLLM 时另开环境，起服务时用 nohup 挂后台，再到控制台把容器内端口映射出去。按小时的实例适合演示，长期挂着不划算。

后两条跨机器，目标端三步完全一样，差别只在源端怎么把补丁取出来：

源端 · AutoDL
有 SSH，直接 scp 补丁在 /root/autodl-tmp/saves/ 一条 scp 传到目标机
数据盘关机还在，先关实例再传更省。
源端 · 魔搭
无原生 SSH、入站端口封 补丁在 /mnt/workspace/ 下 走 OSS 中转，或界面下载再传
36 小时额度别拖，传完就关实例。
# 目标端三步：搬运 → 装基座 → 改路径
scp -r 源机:补丁目录 ./cls_adapter          # ① 补丁搬过来（40 MB）
modelscope download --model Qwen/Qwen3-1.7B \
  --local_dir /root/models/Qwen3-1.7B        # ② 基座重新下（3.4 GB，不搬）
# ③ 改 adapter_config.json 里的 base_model_name_or_path
#    改成目标机上的基座路径，否则服务起不来

# 起服务：--lora-modules 指向新路径
vllm serve /root/models/Qwen3-1.7B --served-model-name cls-base \
  --enable-lora --lora-modules cls=./cls_adapter \
  --max-lora-rank 16 --max-model-len 1024 --port 8000
跨机器唯一的验收标准到新机器重跑第 4 章那 200 条回测，与离线报告差 0.5 个点以内才算搬成功。换机器不重验，等于没验——这是跨机器最容易漏的一步。
三处别只搬一半cls_adapter/ 只是补丁；service/ 里的 label_stats.json 决定候选集，serve_cls.py 里的 PROMPT 决定模板。少搬一样，分数就变了。
  • 挂载不合并：40 MB 换版本，好回滚、能并存；基座不进包，只记名字。
  • checkpoint 目录本身就是 adapter，挑一个拷出来就完事，没有格式转换。
  • 一条 vllm serve 挂两样东西，请求里 model 填适配器名——填基座名，等于前面那轮微调（fine-tuning）白做了。
一句话带走起服务最容易错的不是参数，是「你以为调的是补丁，其实调的是基座」——先看 /v1/models 里有没有两个名字。

4测试评估

结论测之前先对尺子。线上和离线不是同一套打分，测出来的数就不算数——先对口径，再看这 50 次打分怎么发出去，最后压一轮。

先对口径

离线报告里那个 accuracy 有前提：「50 候选打分 + 按词元（token）数平均」。线上换一种算法，这个数立刻作废。

要盯的只有三处：模板与 thinking、候选集与 eos（end of sequence，句末符）、长度归一化。

对齐什么离线（eval_cls.py）线上（serve_cls.py）不一致会怎样
模板apply_chat_template(enable_thinking=False)调同一个函数输出带思考段，分数整体偏移
候选集50 类 + eos同一份 label_stats.json + eos少算 eos，概率乘积少一项
打分候选 token 的 logprob 之和 ÷ token 数同一公式长名部法系统性吃亏

第一条最容易漏。对照一下两种做法的后果：

错法：让模型自由生成
prompt: 这问题该走哪部法？ 输出: 民法典（合同编） → 不等于任何一个标签，判错 → 它其实知道，只是说多了
准确率凭空掉一截，还查不出原因。
对法：50 个候选逐个打分
候选: 民法典 / 刑法 / 劳动法 … 逐一算 logprob，取最大 → 输出必在标签集内 → 顺手得到 top-3
和评测同一套尺子，数字才对得上。

打分本体只有十来行，其中三处是「口径」：

# scripts/serve_cls.py · 一个候选怎么算分
tail = label_ids[label] + ([eos] if eos is not None else [])   # ① 带上 eos
payload = {"model": MODEL, "prompt": prefix_ids + tail,
           "max_tokens": 1, "temperature": 0.0,
           "prompt_logprobs": 0}                              # ② 要 prompt 的 logprob
body = (await client.post("/completions", json=payload)).json()
plp = body["choices"][0]["prompt_logprobs"]
total = sum(plp[len(prefix_ids) + j][str(tid)] for j, tid in enumerate(tail))
score = total / len(tail)                                      # ③ 按 token 数取平均
口径怎么验：抽 200 条考卷走服务把 data/cls/export/test_eval.jsonl 前 200 条的 question 发出去，回来的 label 和文件里的 label 对一遍，算命中率。与离线同批样本差 0.5 个点以内算对齐；差出一个点以上，回来逐条对那三处。
thinking 没关Qwen3 默认会思考。不传 enable_thinking=False，模型先生成一段思考再给答案，概率分布整个变了——这不是「效果差一点」，是「尺子换了」。训练、评测、线上三处必须同一个值。
「按 token 数平均」为什么不能省「民法典」3 个 token，「国际刑事司法协助法」9 个。直接加总比大小，长标签天然吃亏——混淆矩阵里那批「该判长名却判短名」的错案，原因是代码不是模型。

50 次打分

一次分类在服务端是 50 个子请求；前缀缓存把 49 份公共前缀压成一份，代价接近一次批处理前向。

服务本体是个薄壳，三段：拼模板、并发打分、取最大。

# scripts/serve_cls.py · 服务本体（只留主要三段）
async def classify(question: str) -> dict:
    prompt_ids = build_prompt_ids(question)             # 与评测同一个模板函数
    scored = await asyncio.gather(*(score_one(lab, prompt_ids) for lab in _LABELS))
    ranked = sorted(scored, key=lambda kv: -kv[1])
    return {"label": ranked[0][0], "score": round(ranked[0][1], 4),
             "top3": [{"label": l, "score": round(s, 4)} for l, s in ranked[:3]]}

@app.post("/classify")
async def classify_api(req: Ask):
    return await classify(req.question.strip())

第一次接新版本，先探字段 
python scripts/serve_cls.py --probe "公司拖欠我三个月工资怎么办"
把一次打分的原始 JSON 原样打出来。不同 vLLM 版本字段名可能不一样，不要照着文档猜，先看它实际返回什么——这一步能省掉半小时的瞎改。
别想着「把 50 个候选写进一个 prompt 让模型自己挑」它只会给你一段话，不会给你 50 个分数。要分数只有一条路：每个候选单独算一次。一次分类之所以不是 50 倍慢，靠的是前缀缓存，不是靠把请求合并。

压测算账

对外承诺看 P95，不看平均值；单卡能扛多少，压出来才算数——参数量和 benchmark 都替不了你自己这台机器。

数要填你机器压出来的。压完只看三件事：

三行读数，对应三个动作
① 趋势并发翻倍 P95 近似翻倍 → 后端在排队，调 --max-num-seqs 或加卡
② 余量P95 基本不变、吞吐还在涨 → 还有余量，这一档可以放心放量
③ 错误503 或大量超时 → 后端过载，先看 --max-num-seqs 和显存；客户端超时要大于服务端的 8 秒，否则服务端还在算、客户端已放弃重试
20 个样本时，P95 就是「第二慢的那条」样本越少，分位数越像极值。要对外承诺延迟，每档至少 100 个请求；20 个只够看趋势。

算账只要三个数：卡时费、每小时能处理多少、请求量。

# 按满载估算，实际留 30% 余量
每小时能处理 ≈ 3600 ÷ (平均延迟秒) × 并发
单次成本     ≈ 卡时费 ÷ 每小时能处理
每天成本     ≈ 卡时费 × 24          # 7×24 开机，与请求量无关

拿 P95 替平均延迟也能算，结果偏保守——对外报价安全，别当真实吞吐。

项自建（一张 24G 卡）云端托管
固定成本卡时费 × 开机时长0
变动成本≈ 0（同一张卡多打几次不多花钱）按输入输出 token 计费
单次成本卡时费 ÷ 每小时能处理token 数 × 单价
划算区间请求量足够大，把卡时费摊薄请求量小、波动大

这张表最反直觉的一行是「变动成本≈0」：卡开着就在烧钱，不管你一次还是十万次。所以自建的门槛不是技术，是量。

云端托管省的是运维；代价是补丁不在你手里、换平台要重训。

只测并发 1 就对外报延迟单线程下每一项都漂亮，上线 20 个人同时问，P95 直接翻十倍。压测的意义就在这——把你不敢想的那个并发数提前试一遍。
  • 三处必须同口径：模板与 thinking、候选集含 eos、按词元数归一化。
  • 抽 200 条考卷走一遍服务，与离线差 0.5 个点以内才算对齐。
  • 一次分类 = 50 个子请求，公共前缀只算一次；对外报 P95 不报平均值。
一句话带走报告上的 accuracy 只在「线下怎么测、线上就怎么测」时成立——尺子换了，之前所有数字都要重测。

5交付与小结

结论最后一步不是写总结，是把服务交出去：一页文档写全六要素，回滚压到改一个名字。收完尾，回头数一下四段交付有没有缺的。

交付文档

接入文档六要素写不全，接手的人一定会来问你；回滚要能在改一个名字之内完成。

要素写什么漏了会怎样
地址与鉴权base_url、要不要 token对方连不上，先怀疑网络
模型名model 字段填 cls404，还以为是服务挂了
入参出参一个完整的请求 / 响应例子对方照着猜字段，来回三轮
超时与重试客户端超时 > 服务端；重试 1 次重试风暴，越压越崩
错误码400 / 503 各代表什么分不清是自己传错还是服务挂了
版本与回滚当前版本号 + 回滚一条命令出事没人敢动

## 部法分类服务 · 接入说明

- 地址：http://10.0.0.12:8100     鉴权：内网，无 token

       "top3": [{"label": "劳动法", "score": -0.0312}, ...]}

- 超时：客户端 10s，服务端 8s；失败重试 1 次，不要重试 503
- 错误码：400 入参空或超 1000 字；503 后端不可达
- 回滚：把 model 从 cls_new 改回 cls，无需重启

最后一行有个前提：升级时两个版本都挂在同一进程里。只挂了一个，回滚就得重启服务。

回滚为什么是「改一个名字」--lora-modules 一次挂两个版本，切版本只是调用方改 model 字段。发布也一样：先让 5% 的流量走 cls_new，盯一天 P95 和错误率，没问题再全量。
上线之后每周要做的一件事
回归拿固定的 200 条考卷跑一遍，accuracy 掉超过 1 个点就查数据分布变了没有
留旧版旧 adapter 不许删——它是你唯一的一条退路
看长尾P95 比昨天高 50% 就该看日志，别等用户投诉

这一课改了什么

四层各动一处，训练脚本和评测脚本一行没动——改动面越小，出事时越查得动。

层这次动了什么没动的部分
权重层40 MB 补丁挂到基座上基座权重一个字节没改
打分层从本地函数调用换成 HTTP公式、候选集、模板全照旧
服务层新增一个 FastAPI 薄壳训练与评测脚本一行没动
运维层加了版本号和回滚方式不引入网关、编排、监控栈

三条自检

每一步都能单独验，不用等全链路跑通
① 挂上没curl /v1/models 里同时有 cls-base 和 cls
② 口径对没200 条考卷走服务，accuracy 与离线报告差 ≤ 0.5 个点
③ 账算清没P95、吞吐、单次成本三个数都是自己压出来的
下一步这套服务现在只会答 50 部法，不知道「问题该不该问法律」。往前一步是拒答（refusal）：拿一批非法律问题压进去，看它有多自信地乱答——那个分布，决定了上游要不要加一道闸。
  • 接入文档六要素写全，回滚要能在改一个名字之内完成。
  • 上线之后还有三件周常：跑回归、留旧版、看长尾。
  • 全课一条主线：线上和离线是不是同一把尺子——尺子一样，数字才作数。
一句话带走交付的判据是「换个人能不能接上、出了事敢不敢动」——两问都过，这套服务才算交出去了。
