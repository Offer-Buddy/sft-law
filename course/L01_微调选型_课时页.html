L01微调选型15 课 · 第 2 课

先定靶子，再定工具——微调选型的八个判断

这一课不讲某个具体项目该怎么选，只讲判断顺序。前四环定靶子：需求 → 数据 → 验收 → 任务；后四环定工具：基座 → 方法 → 框架 → 平台。每一环给一条判断依据、一条一票否决项。八步走完，换成任何任务都能自己下结论。

1选型总览 2定需求 3看数据 4定验收 5定任务 6选基座 7选方法 8选框架 9选平台 10小结
课程目标三档都过，这课才算拿到
档位学完你能做到怎么算达成
写出画出八环决策链，说清前四环和后四环各在定什么白纸画一条链，八个框顺序不错，每段能用一句话说清这段在定什么
跑通给一个陌生需求，能走完前四环定出任务形态，再给出工具层选型任给一个场景，能填出数据 / 验收 / 任务 / 基座 / 方法五格，不许写「差不多都行」
说清解释为什么「验收」排在「任务」前面——为什么任务不是挑出来的，是被夹出来的举例：把验收从「有客观数」换成「人眼看着还行」，能说出任务形态为什么跟着变
不处理：多卡并行的参数调优细节、推理服务化（vLLM / TGI）的部署调参、数据清洗与构造的具体做法；也不针对任何具体项目——这一课只给判断顺序，落地放到后面的课。

1八个「选」不是并列题，是前后两段

结论前四环定靶子，后四环定工具。靶子没定就挑框架，等于先买钻头再想打哪个孔。第一问不是「用哪个框架」，是「要解决什么、手上有什么、拿什么算解决」。
环节它决定什么一票否决项（什么情况直接否）
定需求整条链往哪走说不清「现在哪一步在失败」→ 先回去翻日志，别急着选型
看数据任务最多能做到多重标注字段对不上你要的输出 → 换任务，别硬凑
定验收训完算不算成了说不出拿什么指标量 → 别开训，训了也没法交差
定任务输入输出长什么样做完没法验证 → 换形态，别硬训
选基座语言底子、参数上限、许可能不能用许可有传染性（AGPL / GPL）→ 直接换
选方法要不要改全部参数、显存花多少全参显存超出你的卡 → 退回 LoRA / QLoRA
选框架用界面还是写代码、能不能改 loss要改 loss / 自定义评估 → 别用黑盒框架
选平台试错速度、预算、环境风险配环境超过一小时还跑不通 → 换平台
最常见的翻车一上来比 LLaMA-Factory 和 ms-swift，比完发现数据里根本没有能当标注的字段，任务得整个换，框架白比。工具层的选择成本最低、返工代价最大——正因为它是最后才该动的那一层。
这一章钉住了三件事
  • 钉住了：选型是前后两段，前四环定靶子、后四环定工具；八环有先后，不是八道并列选择题
  • 不这么做会：先挑框架再回头看任务，发现框架选得根本不对，推倒重来
  • 下次遇到同类问题，先问：我要解决哪一步失败、手上有什么数据、拿什么量——三个答不出，后面的选型全是空转
带走先定需求、数据和尺子，再谈选什么——顺序反了，选得再细也是白选。

2定需求：先定位失败在哪一段

结论需求不是「让模型聪明一点」，是「现在哪一步在失败」。说不清失败的那一步，就不该往下走——因为不同段落对应完全不同的药，微调只治其中一段。

把任何一个带模型的应用拆开看，都是四段：理解输入 → 取资料 → 组织输出 → 兜底规则。失败可能落在任何一段，而每一段的药不一样。

业务描述的现象大概率在哪一段该动什么
用户说的话，模型听不懂他想要什么理解输入意图分类的微调，或补几条路由规则
资料库里有，就是检索不出来取资料换检索方式、优化 query、加语料——不是模型不会说话
资料找到了，答得啰嗦、答跑偏、格式不是要的组织输出这才是微调的主场：改的是输出的形式和习惯
该拒答的答了，该答的拒了兜底规则调阈值和规则，跟模型能力关系不大
一个很常见的误判：把「查不到」当成「答不好」。用户说「它答得不对」，你去训模型；实际是检索那一段没取到资料，模型在没有依据的情况下硬答。这一类需求训多少轮都没用——得先看日志，确认资料到底进没进 prompt。

需求拆成三问，答完才往下走

问什么答成什么样才算过关
谁在什么场景失败具体到一类用户、一个入口、一个动作。不能是「用户觉得不好用」
现在是怎么失败的能指到上面四段里的某一段，最好能从日志里翻出例子
做成什么样算解决一句话能说清，且这句话后面能翻译成指标——翻不成的，第 4 章会拦下来

排掉四条不微调的路，剩下的才是微调的地盘

手段改的是什么时候它就够了什么时候不够
改 prompt指令输出偶尔跑偏、格式不稳，加几条约束就收住了约束写到几百字还是压不住，每次都在跟自己较劲
加检索、换 embedding取资料要新知识、要溯源、库里没有的东西query 侧本身就对不上，检索再强也只能在错的附近找
加规则 / 后处理输出管道错法能枚举完，正则和词典能覆盖说法无穷无尽，规则库永远追不上新表达
换更大的模型能力上限任务要推理深度，小模型确实扛不住只是要改个说法，大模型是纯浪费，还更慢更贵
微调输出习惯形式固定、量大重复、且有办法量化验证要新知识、要可溯源、样本太少——换个手段
关键区别这五条不是竞品，是叠加关系，各有各管的一段。真实项目里通常几条一起上；微调只是其中一条，它被选中的条件是：失败发生在「输出形式」这一段，而且这个形式能被量化。
这一章钉住了三件事
  • 钉住了：需求先定位到四段里的某一段，微调只治「组织输出」这一段
  • 不这么做会：把检索问题当模型问题，训了半个月，上线还是查不到
  • 下次遇到同类问题，先问：现在到底是哪一步在失败——是听不懂、取不到、说不好，还是规则没卡住？
带走微调不是万能药，它是四段里的一段专用药——先确诊，再开方。

3看数据：有什么料，决定能训什么形态

结论数据不是越多越好，是标注字段对不对。手上那批数据长什么形状，直接决定了你能训出什么任务——这一步经常比选模型重要十倍。

拿到一份数据，先别看条数，先看它长什么样。几种形态对应的任务，几乎是一一对应的。

数据形态长什么样能训什么任务
输入 + 目标输出（配对）一句话 → 另一句话
问句→标准答案句、口语→书面、A 语言→B 语言		改写、翻译、格式转换、风格迁移——本质都是「把一句改写成另一句」
输入 + 标签一段文本 → 一个类别或几个字段
「这句话属于哪类意图」「这段里有哪些要素」		分类、意图识别、信息抽取、打标
输入 + 偏好同一个问题 → 两个回答 → 哪个更好偏好对齐（DPO 这类方法），不是监督微调
只有原始语料大量没有标注的文本只能做继续预训练，做不了监督微调——没有「标准答案」可学
核心一句你想训成什么，取决于数据里哪个字段能当「正确答案」。想训问答，但手上只有「问句 + 分类标签」，那就只能训分类器；想训分类，但手上全是长答案，那就得先抽标签。反过来硬凑，训出来的东西一定跑偏。

第二个问题：够不够

  • 量级：窄任务（分类、格式转换、单轮改写）几百到几千条就能见效；要改口径、要多轮对话，往往得上万。判断标准不是绝对条数，而是覆盖够不够——把任务拆成若干子情况，每种情况至少几十条。
  • 质量：一千条干净、目标一致的数据，胜过一万条目标混乱的。数据里混进 5% 目标不对的样本，模型学到的就是那 5% 的习惯。
  • 分布：训练集的分布要贴着线上真实输入。线上是口语，你拿书面语训，训完在线上等于没训。

三个常见缺口，开训前必须知道

缺口现象怎么补
分布不符训练数据是书面语、规范表述，线上输入是口语、错别字、缩写把训练输入改写成线上那副样子，标注保持不变
没有考卷数据只能拿来训，没有一份能测「好没好」的独立测试集从数据里切一批出来单放，人工过一遍，锁死不再参与训练
类别失衡某一类占八成，其余均分剩下两成按类别配额采样，别让少数类在训练里等于消失
数据这一关的结论只有一句：它决定任务的上限。不是「数据量不够」，很多时候是标注字段决定任务形态——手里那批数据只能学「把 A 变成 B」，那就别指望训出「回答问题」的能力。想换任务，先去换数据，不要在模型上硬拧。
这一章钉住了三件事
  • 钉住了：先看数据形态，再看条数——配对数据训改写，标签数据训分类，只有语料只能继续预训练
  • 不这么做会：拿错形态的数据硬训，训出来的模型在目标场景上完全不对，还以为是自己调参不行
  • 下次遇到同类问题，先看：这份数据里哪一列能当「标准答案」——找不到，就先去造数据
带走数据形状决定任务形状——先看标注字段，再看条数。

4定验收：先有尺子，再开训

结论验收标准必须在开训前写在纸上。写法就一句：同一套题，训前量一次，训后再量一次，差多少一目了然。没有这个数，训完只能说「感觉好一点」。

第一件事：你的任务到底能不能量化

不是所有任务都好量。先给任务对号入座，再看有没有尺子。

任务类型能用的指标坑在哪
分类 / 意图准确率、F1、混淆矩阵要有一份人工标过的测试集；类别失衡时只看准确率会被带偏，要看 F1
抽取 / 结构化字段级准确率、整条完全匹配率只看整条会掩盖问题——十个字段里错一个，整条也算错
改写 / 生成字面重合类指标（BLEU / ROUGE）和人感差得远改写没有唯一正确答案，跟参考答案字面不一样不代表错
对话 / 问答人工评分、两两对比、任务完成率人工评分要定评分表，否则两个人打出两套分
最有用的一招生成类任务自己没尺子，就把尺子挂到下游。改写本身没法打分，但「改写后去检索，目标文档能不能进前 k」能打分；问答好不好没法直接量，但「用户有没有追问同一件事、有没有转人工」能统计。指标不一定要长在模型身上，能长在链路上也行。

这一招为什么重要：它把「没法验证的任务」变成「可以验证的任务」。很多看起来只能人眼看的活儿，挂到下游都能找出一个客观数。找不出来，才是真的该重新考虑要不要做。

第二件事：基线

# 一把尺子的全部逻辑，和任务类型无关
for case in testset:              # 一套固定的题，训前训后都用它
    out  = model(case.input)      # 训前用原始方案，训后用微调后的方案
    ok  += check(out, case.gold)  # 对错判断，或下游指标是否达标
score = ok / len(testset)

训前跑出来的那个数，就是基线。它是后面所有比较的地基。没有基线，「提升了」这句话没有任何意义——你不知道从哪儿提的，也不知道提了多少。

比数字时，三样必须一样：同一套题、同一个下游版本、同一个评判标准。中间换了检索库、换了 embedding、换了评分人，两次数字就不能比——那不是提升，是换了一把尺子。要换就整套重测，基线一起重跑。

第三件事：验收单，三行

开训前填好，训完对着勾
① 主指标
用哪个数、基线多少、要到多少。这条线自己定，但必须在开训前写下来——不能训完再看着结果定标准
② 回归
微调会不会把原来会的东西训坏。要有一组「本来就会」的题，训后重跑，掉太多就是训过头
③ 成本
延迟、显存、单次推理开销。模型接在线路上，多出来的每一毫秒都是用户在等
为什么要排在这里验收排在任务前面，是因为尺子决定形态。能量化、有客观数，任务就能定成「输出一句话」这种窄形态；只能人眼看、谁也说不清好坏，那选什么任务都不算数——因为你无法证明它变好了。
这一章钉住了三件事
  • 钉住了：验收要在开训前写下来——主指标、回归、成本，三行缺一行不开训
  • 不这么做会：训完拿模型去评审，被问「好了多少」只能答「感觉顺畅多了」，等于没答
  • 下次遇到同类问题，先问：这个任务有没有客观数——自己身上找不到，就往链路下游找
带走没有基线的提升是感觉，不是结论——尺子先立，模型后训。

5定任务：三样一夹，形态自己浮出来

结论任务形态不是挑出来的，是需求、数据、验收三样夹出来的交集。四类常见形态，对数据、对验收的要求完全不同。
形态输入 → 输出数据要求验收怎么量
分类一段文本 → 一个类别输入 + 标签准确率 / F1，最容易量
抽取一段文本 → 若干字段输入 + 字段标注字段级准确率，好量
改写一句话 → 另一句话输入 + 目标句（配对）自己没尺子，挂下游量
生成一个要求 → 一段长文本输入 + 参考答案（配对）最难量，通常要人工

怎么用三样去筛

拿三个问题依次过一遍，每过一关砍掉一批选项，剩下的就是能做的：

三道筛子，依次过
① 数据有配对吗
要训改写，就得有「原文 → 目标句」这种配对。只有标签、没有目标句，改写直接出局
② 验收量得出吗
能找出一个客观数（自己身上或下游）就能进；只能「看着还行」，出局
③ 下游接得进吗
训出来的东西要能插进现有链路。和链路上已有的能力重复，硬接进去就是两个模块抢一个活

三道过完，通常只剩一个形态。这时候不用纠结「哪个更酷」——剩下的那个就是答案，其余的都被数据或验收否掉了。

第三条最容易被漏。一个模型训得再好，如果它的输出在链路上没人接、或者和已有模块功能重复，价值就等于零。定任务的时候就要问：这个输出，下一步谁消费、怎么消费。
这一章钉住了三件事
  • 钉住了：任务形态是三道筛子的结果——数据有配对、验收量得出、下游接得进
  • 不这么做会：凭感觉挑一个「听起来很酷」的任务，训完发现数据对不上、指标量不出、还接不进链路
  • 下次遇到同类问题，先问：这个形态，数据里有对应配对吗、能量吗、下游接得进去吗——三问答完，任务自己就定了
带走任务不是挑出来的，是被需求、数据、验收三样夹出来的。

6选基座：许可 → 语言 → 规模

结论基座的判断顺序是许可、语言、规模，三步依次过。榜单分数不参与决策——它测的是通用能力，跟你这个窄任务关系不大。

三步判断，顺序不能反
① 许可
第一眼看 license。Apache 2.0 / MIT 最省心；AGPL / GPL 有传染性，闭源产品用之前要掂量；自定义协议（GLM、Gemma）要逐条读。训完才发现不能商用，前面全白干——所以它排第一
② 语言

③ 规模
最后才看参数档，结合你的卡和试错轮次算。同样两天，小模型能试十个配置，大模型只能试两个，而微调的效果八成来自试

小1.7–4B8–12 G舒服窄任务改写、语体转换、单轮指令长文生成、多轮、复杂约束
中7–9B16–20 G刚好通用助手、多轮、稍复杂的指令显存一紧，batch 开不大
大14B24–32 G要 A100需要推理、长文输出个人和小团队成本不划算
超大32B+ / MoE48 G 起别想追平闭源效果不在这一课范围
为什么任务窄就该用小模型。改写靠的是语感和词表，不靠推理深度；知识由检索提供，参数里多出来的通用知识在这类任务上一分用不上；模型越小，同样时间里能试的配置越多；它还接在链路上，每次请求都要过一遍，几十毫秒和几百毫秒，用户能感觉到差别。不是「便宜所以选小的」，是「大模型多出来的优势这一档用不上」。
现成的垂域模型为什么不直接拿来用。三个常见的坑：底座旧（架构落后一两代）、任务不对（训的是答题，不是你要的那件事）、许可有传染性（不少开源垂域模型是 AGPL）。真正值钱的是它们的数据构造和评测思路，不是权重。
这一章钉住了三件事
  • 钉住了：选底模的顺序是许可 → 语言 → 规模，榜单分数不参与决策
  • 不这么做会：拿一个 GPL 的垂域模型训两周，要商用才发现许可传染，全白干
  • 下次遇到同类问题，先看：模型卡里 license 那一行，再看语料厚不厚，最后才算显存账
带走先看许可，再看语言，最后看卡——顺序反了，白干一场。

7选方法：全参、LoRA、QLoRA，由显存账定

结论方法不是偏好问题，是显存问题。全参≈参数量 × 12 字节，扛不住就退 LoRA，还紧就上 QLoRA——这是一条顺序，不是三个并列选项。
方法改多少参数显存大致怎么算什么时候选它
全参100%参数量 × 12 字节起（还要加激活值）数据量上万、要彻底改口径、手上有大卡
LoRA约 1%（旁挂低秩）基座权重 + 很小的补丁和优化器状态默认选项：不动原权重，只训补丁，几百到几千条就能见效
QLoRA约 1%基座量化到 4bit 后只剩四分之一左右卡不够时的标准解：4bit 量化基座 + LoRA，训练逻辑完全一样
算一遍就懂全参的显存大头是三份：权重、梯度、优化器状态，大致按每参数 12 字节估。1.7B 的模型就是 1.72B × 12B ≈ 20.65G，还没算激活值——24G 的卡只剩 3G 给它，基本开不动。这就是为什么个人和中小团队几乎都用 QLoRA：不是它先进，是它装得下。
别把「量化」理解成省精度。NF4 不是均匀砍 16 档，是按正态分布分档——中间密、两头疏，越常用的值分得越细。所以 4bit 基座压到原来的四分之一，窄任务的效果几乎不掉。结论记牢：QLoRA 是「省显存」不是「省效果」。
反过来也有坑：卡够大不等于该开全参。数据只有几百上千条时，全参更容易把预训练学到的东西冲掉（灾难性遗忘），最后反而比 LoRA 差。方法是跟着「数据量 + 显存」两个条件一起定的，不是越重越好。
这一章钉住了三件事
  • 钉住了：方法由显存账定——全参扛不住就 LoRA，还紧就 QLoRA，这是顺序不是并列
  • 不这么做会：拿大模型在 24G 卡上硬开全参，OOM 三次之后开始怀疑自己不适合这行
  • 下次遇到同类问题，先算：参数量 × 12 字节，和你的卡比一比，答案自己就出来了
带走显存账先算，方法后选——算一遍，比背十个方法有用。

8选框架：技术、框架、加速，分三层看

结论「选个框架」把三件事混成了一件：改哪里（微调技术）、谁跑循环（训练框架）、怎么提速（加速与并行）。三层可以叠、不互斥，顺序是先技术、再框架、最后加速——反了就会变成「先挑工具，再想拿它干什么」。

一、技术层：先定改哪里

上一章只讲了全参、LoRA、QLoRA 三种主干，这一章把谱系补全。主干之外的都是变体，判断依据还是那两条：改多少参数、值不值这个代价。

技术改哪里可训参数显存代价什么时候用 / 代价是什么
全参 Full FT全部权重100%12–16 字节/参数数据上万条、要彻底改口径、手上有 A100 级卡。几百条数据开全参，只会把原有能力冲掉
LoRA旁挂低秩矩阵，原权重冻结0.1%–1%基座 + 极小补丁默认首选：几百到几千条就见效。秩 r 和 target_modules 选错，等于白训一轮
QLoRA4bit 量化基座 + LoRA同 LoRA基座压到约 1/424G 卡训 7B–14B 的标准解。每步慢两三成，这是反量化的代价，不是配置错了
DoRA权重拆成幅度和方向，只训方向同 LoRA稍高于 LoRA小秩下比 LoRA 稳、掉点少。较新，部分框架还没接全，先确认文档再上
LoRA+A、B 两组用不同学习率同 LoRA不变嫌收敛慢时的零成本加速。只改超参，收益看任务，不是必开项
AdaLoRA按重要性动态分配秩自适应高于 LoRA不知道该给哪层多少秩时用它自动分。实现慢、参数多，能手工调就别上
(IA)³每层学几个缩放向量万级极低只有几百条数据、先看数据里有没有信号。能力上限低，验证完要换回 LoRA
Prefix / P-Tuning每层前挂可训练前缀0.1% 以下低生成类任务、复现早期论文。要吃上下文长度，现在新项目少用
Adapter在层间插瓶颈模块1%–5%低一个底座挂多个任务，按需切换。推理多一层延迟，必须合并才消得掉
冻结部分层只训最后几层或 embedding看冻结范围最低快速 baseline、判断数据值不值得继续做。别指望它出成品
一条判据除了全参，其余九种都在「少改一点、多省一点」这条轴上移动。参数越少，能改的东西越浅——所以判断顺序是：先看数据够不够动全参，不够就往 LoRA 退，再不够就往 (IA)³ 这类极端省参的方向退，而不是反过来「先挑个听起来先进的」。

二、信号层：教什么，决定要什么数据

技术解决「改哪里」，信号解决「拿什么教」。这一步的瓶颈不在算法，在你手上有没有那种形状的数据。

方法数据长什么样显存与工程什么时候用 / 代价是什么
SFT 指令微调输入 + 目标输出，一问一答成对一个模型，最轻九成任务都从这一步开始。数据质量的影响远大于数量，两千条干净的胜过两万条脏的
蒸馏大模型生成的输入输出对一个模型（离线造数据）没有人工标注、但有可用的大模型。教师答错，学生会一字不差地照抄
DPO同一输入下，好答案 / 坏答案成对当前模型 + 参考模型两份权重SFT 之后想把「好坏差距」拉开。偏好对难造，且容易把模型训得又硬又短
ORPO偏好对，把 SFT 并进同一步不需要参考模型显存紧、想一步到位。方法较新，框架支持参差，先跑通再信
KTO只要「这条好 / 这条差」，不必成对同 DPO有大量单条反馈、配不成对时。标签噪声敏感，脏标签会直接教坏
GRPO问题 + 能自动判对错的答案组内多次采样，用显存换效果数学、代码这类有判分器的任务。判分器写歪，训出来的就是「会骗判分器」
PPO / RLHF提示 + 奖励模型打分四个模型同存，工程最重做通用对齐的大团队。个人和小团队先别碰，调不动的部分远多于能调的

顺序上有个经验：SFT 没做好就上偏好对齐，等于在歪地基上加层。先把 SFT 的损失降下来、抽几十条样本人工看一遍，再考虑 DPO 这一类。

三、工程层：谁跑循环

技术和信号定了，接下来是「谁来写那几百行训练循环」。这一层不改效果上限，只改你一天能试几个配置。

框架出身强项什么时候选它 / 代价是什么
LLaMA-Factory社区（北航系起）一个 YAML 从训练跑到导出，自带网页界面，中文文档全想最快看到第一个 loss，或要给不写代码的人演示。封装深，想改内部逻辑得翻源码
ms-swift阿里魔搭和模型库、Notebook 是一家，模型覆盖最广，多模态也管国内网络环境、用魔搭的模型和算力。版本迭代快，接口常变，锁版本再开工

四、加速层：怎么更快

加速不是「开了就赚」——每一项都在拿时间或精度换显存。知道它换的是什么，才不会被某个开关的副作用吓到。

手段换到了什么代价什么时候开
梯度检查点激活显存省一半以上慢两成左右默认开。显存不够时第一个动的就是它
FlashAttention-2注意力更快、更省显存要 Ampere 以上架构默认开。老卡（V100 / T4）用不了，别装
4bit 量化基座显存压到 1/4反量化让每步变慢卡装不下 fp16 基座时
8bit 优化器优化器状态再减半少量精度损失长序列、显存卡在临界线上时
序列打包吞吐翻两三倍边界没切干净会串样本短样本占多数时开，开完抽一条出来验证边界
DeepSpeed ZeRO-3参数、梯度、优化器切到多卡卡间通信变多，调参变复杂单卡彻底放不下时
Unsloth kernel单卡提速并省显存只覆盖主流模型、只认 Linux单卡、模型在它支持列表里

五、三种组合，对应三种人

先想清楚你现在缺的是透明、速度，还是规模
要透明
手写 transformers + peft + accelerate。三十行，loss 怎么算的、梯度有没有走，全在眼前。第一次做微调建议走这条，出问题知道往哪查
要速度
LLaMA-Factory 或 ms-swift 打底，单卡再叠 Unsloth。要试的配置多、卡只有一张，这一组最划算——省下来的时间直接变成试错轮次
要规模
Axolotl 或 ms-swift 配 DeepSpeed ZeRO-3，再往上是 Megatron。到这一步调的是通信和分片，不是学习率

六、三十行能看清什么

不管最后用哪个框架，这三十行都值得亲手写一遍——它把「微调」拆成四个动作：换精度、挂补丁、包数据、开训。框架只是把这四步写成了配置。

# ① 换精度：基座压到 4bit，显存降到四分之一
bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    MODEL_ID, quantization_config=bnb, device_map="auto"
)

# ② 挂补丁：只训旁挂的低秩矩阵，原权重一动不动
lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora)
model.print_trainable_parameters()   # 看一眼：通常不到 1%

# ③ 包数据：对话模板必须和基座训练时用的那套一致
text = tokenizer.apply_chat_template(msgs, tokenize=False)
batch = tokenizer(text, truncation=True, max_length=2048)

# ④ 开训：真正需要改的其实只有这三处
args = TrainingArguments(
    learning_rate=2e-4,            # LoRA 比全参大一个量级
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,
    gradient_checkpointing=True,
    bf16=True,
)

写完这段再去看框架的配置文件，你会发现那些看不懂的字段，对应的就是这四步里的某一行。先有这三十行，框架才是快捷键；没有它，框架就是黑箱。

七、五个坑

一个框架一个环境。LLaMA-Factory、ms-swift、Unsloth 对 transformers 和 trl 的版本要求经常互相冲突，装在一个环境里就是给自己挖坑。按项目建 venv，别图省事共用。
Unsloth 的 kernel 只认 Linux。它靠自定义 Triton 内核提速，官方支持 Linux；Windows 下要么 WSL，要么直接上云，别在原地反复重装。
对话模板不一致，训完效果断崖。基座训练时用什么模板（角色标记、特殊 token、结尾符），微调时必须一模一样。框架默认值不一定对，开训前先把一条样本 decode 出来看一眼。
4bit 权重不能直接合并。要合并回基座，先把量化权重反量化成 fp16 再 merge；直接在 4bit 上合并，精度掉得比训练本身还多。
框架的默认超参会悄悄改你的实验。序列打包默认开、cutoff_len 默认 2048、学习率默认 2e-5 量级——这三项在你不知情的时候就已经决定了结果。第一次跑，把配置里的默认值逐条读一遍，比盲目调参有用得多。
这一章钉住了三件事
  • 钉住了：框架是三层不是一层——技术定改哪里、框架定谁跑循环、加速定多快，顺序是先技术后工程
  • 不这么做会：把 LLaMA-Factory、Unsloth、DeepSpeed 当竞品各学一遍，最后既说不清它们各管什么，也修不了自己的 loss
  • 下次遇到同类问题，先问：要改的东西在权重里还是在数据里、一天能试几个配置、有没有多卡——三个答案直接对应三层
带走先手写三十行，再让框架当快捷键——不然它就是个黑箱。

适合：要把模型快速起成服务或 demo，应用模板点几下就能用。配什么：模板偏推理和可视化，微调要走实例自己装框架。注意：另有 Cloud Studio 提供每月一万分钟的 T4 免费额度，只够跑 7B 以下的轻量验证
AI Studio
适合：学生、零预算、先把流程跑通。每日算力点天天刷新，够你一天试两三个小配置。配什么：飞桨的 PaddleNLP 有现成微调套件；PyTorch 也能跑，但环境和额度都不如飞桨顺。注意：V100 跑 7B 的 QLoRA 很慢，只适合验证代码通不通，不适合出结果

三、第二梯队：需要时再往下看

平台特点什么情况会用到
UCloud 优云智算消费级卡按天、按月套餐，大显存卡有独家规格要连续跑几天、按量计费反而更贵时
恒源云 / 矩池云与 AutoDL 同类，价格和卡型各有出入AutoDL 抢不到卡时做备选，账号多备一个不亏
华为云 ModelArts企业级，昇腾国产卡也在里面项目要求国产化或已有华为云账号
火山引擎按量 GPU + 模型服务训练完要顺手做在线推理

四、怎么比：算「一天能试几个配置」

换算一天能试的轮数 ≈ 可用小时 ÷ 单轮耗时。单价只影响总花费，不影响轮数——而微调的效果八成来自试。配环境花掉两小时，等于直接砍掉四分之一的产能，这一项的权重比每小时贵五毛高得多。

拿一组中性数字算一遍：五千条数据单卡跑一轮约 40 分钟，一天能用 8 小时，理论上是 12 轮；如果开机配环境、下模型、调依赖花掉 2 小时，只剩 6 小时，就是 9 轮。同样一天，选「镜像现成」的平台比选「便宜两毛」的平台多试三轮。

四个成本项，只看第一个最容易超预算
算力费按秒或按小时，看得见的那部分，通常只占总花费的一半多
存储费数据盘超出免费额度的部分按 GB 计，关机后仍在收
带宽费下载权重、传数据集都走公网，几十 G 的模型来回几次就是一笔钱
空转费开着 GPU 装环境、读文档、开会——最贵的一项，也是唯一完全能避免的一项

五、五个通用坑

配环境别开 GPU。按量计费的机器空转也在烧钱。能开无卡模式或 CPU 实例就先开，依赖装完、数据传完，再切到 GPU 跑训练。这一条省下的钱，比挑平台省的多。
关机不等于不计费。多数平台关机后仍收存储费，有的还收公网 IP 保留费。跑完先看账单明细，再决定要不要「释放」。
系统盘和数据盘是两回事。重装镜像会清系统盘，数据盘才留得住。训练脚本、数据、输出目录一开始就放在数据盘，别等丢了一次才改习惯。
免费额度有硬限制。空闲自动关机、单次时长上限、同一时间只能开一个实例——长训练不断点续训，跑一半被停就白跑。
数据合规不是小事。含个人信息、病历、身份证号这类数据不能上公有算力平台，先脱敏，或者只在单位的机器上跑。这一条不构成技术选择，构成红线。
这一章钉住了三件事
  • 钉住了：平台按「一天能试几个配置」比，不按单价比；免费额度试跑、按量租卡训练、本地写代码，三处各干各的
  • 不这么做会：开着 GPU 装环境烧掉几十块，或者忘了关机，月底账单比训练本身还贵
  • 下次遇到同类问题，先算：单轮多久、一天可用几小时、配环境要多久——三个数一除，平台自己就选出来了
带走配环境别开 GPU，数据别放系统盘——这两条比挑哪个平台省得多。

10小结

结论八环压成一张判断表。前四环定靶子，后四环跟着靶子走；每一环都有一条判断依据，也都有一个「什么情况直接否」。
环节判断依据一票否决 / 结论怎么下
需求失败落在哪一段定位不到「理解 / 取数 / 输出 / 兜底」中的某一段，就别往下走
数据哪个字段能当标准答案配对训改写、标签训分类、只有语料只能继续预训练；对不上就先去造数据
验收有没有客观数自己身上找不到，就往链路下游找；还找不到，这个任务不该做
任务三道筛子数据有配对、验收量得出、下游接得进——三道过完只剩一个形态
基座许可 → 语言 → 规模许可有传染性直接换；榜单分数不进决策
方法参数量 × 12 字节全参扛不住退 LoRA，还紧上 QLoRA；卡大但数据少也别开全参
框架技术 → 框架 → 加速先定改哪里（全参 / LoRA / 变体）、再定谁跑循环、最后开加速；一个框架一个环境，4bit 权重不能直接合并
平台一天能试几个配置免费额度试跑、按量租卡训练、本地写代码；配环境别开 GPU，数据放数据盘

四条边界，越界就要重做

  • 靶子先于工具。需求、数据、验收没定，后面任何选型都是空转——先补这三样，别急着挑框架。
  • 数据决定上限。手上材料的标注字段和目标输出对不上，任务就得换，硬凑只会训出一个跑偏的模型。
  • 许可一票否决。基座许可有传染性（AGPL / GPL）直接换，别等训完再发现不能商用。
  • 方法跟显存走。先算「参数量 × 12 字节」，扛不住就退 LoRA、再紧就 QLoRA，别硬开全参。

三条自检

从下结论到能开训，每步都能单独验
① 画链白纸画出八环链，前四环是靶子、后四环是工具；每环下写一句你自己那个场景的结论
② 量基线把测试集切出来、锁住，用现有方案跑一遍，把主指标记下来——没有这个数，后面所有比较都不成立
③ 验卡平台开机后 nvidia-smi 可执行、torch.cuda.is_available() 为 True
下一步八环走完只是纸上的结论。下一步是把它变成能跑的东西：从数据里抽训练对、切出能判好坏的测试集、把环境配起来。没有那把尺子，训完你也不知道有没有变好。
这门课留下的判据
  • 判据一：选型是前后两段，靶子定方向，工具跟着走——顺序反了全白选
  • 判据二：每选都有一个一票否决项——说不出需求、数据对不上、验收量不出、许可有传染、显存不够，先看否决项再看优点
  • 判据三：数据看标注字段对不对，不看条数多不多
  • 判据四：验收在任务前面，因为尺子决定形态
带走遇到「该选哪个」，先问需求清不清、数据够不够、指标量不量得出、许可过吗、显存够吗——五问过了，答案自己浮出来。
