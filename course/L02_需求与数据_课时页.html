1这一课只看两件事：需求与数据

结论微调的成败在开训前就定了：需求定错方向，数据定死上限。这两样都不是「想清楚」，是能写在纸上、能量出数来的东西。

上一课把八环的先后讲清楚了，但八环是空的——你知道「要先定需求再看数据」，还不知道这个项目到底治什么病、手上这批料长什么形状。这一课只填前四环里的两格：需求和数据。剩下两格不用另找答案，它们是被这两格夹出来的。

先看全貌。这个项目不做一个法律问答机器人，它只做一件很小的事：把用户的大白话，换成法条里那套说法，然后交给检索器。

「只做翻译」这个定位一次性解决了三件事：

问题翻译器这个定位怎么答的
怎么评测翻译得好不好，丢给检索器跑一遍就知道——对的法条进没进前 5。第 3 章那三组数就是这么来的
会不会抢活下游那个大模型本来就负责答，它答得比我们手上这个小模型好得多。让 1.7B 去答法律题，是拿短板碰人家长板
错了怎么办它只输出检索用的文本，不输出结论。翻歪了顶多是检索偏了，不会给用户一个错的法律意见——法律场景里，这条比准确率重要
这一课的行军图第 2 到 4 章讲需求：这个系统断在哪一段、断得有多厉害、需求最后落成一句什么话。第 5 到 8 章讲数据：料从哪来、每个字段是什么、哪些是陷阱、这批料的形状是什么。第 9 章把两头合上——数据缺的那一列，决定了任务只能是改写。
这一章钉住了三件事
  • 钉住了：这一课只填两格，需求和数据；验收和任务是它们夹出来的，不是另选的
  • 不这么做会：跳过需求直接看数据，看到 23,331 条就觉得「料够多，训问答吧」——方向一开始就歪了
  • 下次遇到同类问题，先问：我这个模型在链路里占哪一格，能不能用一句话说清它不做哪些事
带走先说清只做哪一格，再谈训什么——范围不清的项目，数据再多也训不出能用的东西。

2需求第一问：这个系统断在哪一段

结论上一课说过微调只治「组织输出」。这个项目要绕一个弯：它断在「取资料」，而微调插手的位置，是把用户的问法提前翻成检索器认的话。这是全项目最容易搞错的一处。

四段的框架上一课给过了，这里只把它按到本项目上，看每一段的实际状态。

段落这一段在干什么本项目的情况
理解输入判断用户想干什么：问规定、要流程、要材料、还是发牢骚没问题。用户问的就是法律问题，意图很清楚，不需要分类
取资料从库里把相关法条找出来问题在这一段。用户的说法和法条的说法对不上，对的法条排不上去
组织输出把资料组织成用户看得懂的回答下游大模型干得很好，不需要我们操心
兜底规则该拒答的拒、该转人工的转有阈值规则，和模型能力无关

现场是什么样

用户问：「老板让我天天加班，一分钱加班费都不给，我能要回来吗？」系统答得很像样，引了《劳动法》第四十四条——这条是对的。

换个说法再问：「我们公司天天让我们加班到十点，还不给钱，这算不算违法？」系统答：「根据《民法典》第五百零九条，当事人应当按照约定全面履行自己的义务……」——这条错了，跟加班费没有关系。

同一件事，换个说法就引错法条。这不是模型不会答，是它拿到的资料就是错的。而在法律场景里，引错法条比答不出来更危险——答不出来用户会去别处问，引错了用户会当真。

先做一次归因实验，别急着训

把正确的那条法条直接贴进 prompt，让下游模型答。如果答得又对又全，说明模型的语言能力和法律常识都够用，问题只在「给它的料不对」。这个实验十分钟能做完，但它决定了后面两个月往哪儿使劲。

不做这个实验的代价：直接开始训模型，训完发现答案还是错的——因为检索那一段没动。这时候你会以为是数据不够、参数不对，再训三轮，最后发现方向从一开始就错了。

三条修法，为什么选改写 query

修法改的是这次为什么不选它做主路
换 embedding 模型把向量模型换成更大更强的要重建整个索引、重跑全库；而且鸿沟不在模型容量，在两种语体本身——换个大模型，两种说法还是不像
加 rerank在前 k 条里重新排序有用，但它只能救排序。实测首位命中 66% 说明对的法条进了前 5 却排后面，rerank 能救这一批；没进前 k 的那批它救不了
改写 query把用户的话换成法条的词，再去检索检索器一行不用改，插在入口，坏了能摘掉；而且它和 rerank 是叠加关系，不冲突
为什么改写能治本检索器比的是「两段文本像不像」。用户说「加班费」，法条写「延长工作时间……支付不低于工资的百分之一百五十的工资报酬」——字面几乎不重叠。改写要做的是把左边那句换成右边那套词，让「像不像」这件事重新变得可比。这跟换多大的向量模型没关系。

到这里，需求的形状出来了：一句话 + 一个位置。一句话是「让口语问法能命中对的法条」，一个位置是「插在检索前面」。但「能命中」是个感觉，还得变成数——下一章量给你看。

这一章钉住了三件事
  • 钉住了：这个项目断在「取资料」，微调插手的位置是检索的入口，不是输出端
  • 不这么做会：把检索问题当模型能力问题，训出来的模型答得更流畅，但引的法条还是错的
  • 下次遇到同类问题，先做归因实验——把正确的资料直接喂给下游，看它答不答得对
带走先确认断在哪一段，再决定训什么——训错位置的模型，越训越像样，也越训越没用。

3需求的证据：三组数把「感觉不准」变成一条缺口

结论「用户说不准」不是需求，是抱怨。要把它变成一条能量出来的缺口，得先有一把尺子，再量一次现状——而且这把尺子不能长在模型身上，得挂到下游。

尺子从哪来

上一课讲过一招：生成类任务自己没尺子，就把尺子挂到下游。改写这件事本身没法打分——同一句话可以有一百种改法，跟参考答案不一样不代表错。但「改完之后去检索，对的法条进没进前 5」能打分，而且是硬指标，不掺人眼。

这就是本项目的尺子。它有三个读数，各管一件事：

指标怎么算它回答什么盲区
命中率
hit_rate@5		前 5 条里出现了正确法条，这题算 1找到了没有排第 5 和第 1 一样算中，分不出好坏
首位命中率
top-1		第 1 条就是正确法条排得够不够前只看法条位置，不看答案对不对
平均倒数排名
MRR		正确法条排第几，就取几分之一，全部题目求平均平均排在多前一题有多个正确法条时，按最好的那个算

MRR 的名字有点唬人，算法很朴素：排第 1 得 1 分，排第 2 得 0.5 分，排第 3 得 0.33 分，排到第 5 得 0.2 分。每道题都算一个分，最后求平均。它比命中率更敏感——命中率只看「进没进前 5」，MRR 还看「排得多前」，所以它对排序的变化有反应。

量出来的三组数

条件先钉死，不然这些数没法比：法条库 6,432 条 / 50 部法，向量模型 BAAI/bge-small-zh-v1.5，取前 5 条。

评测集题数命中率@5首位MRR
书面语（全量抽 400）40079.75%—0.6538
书面语（对照组）4077.50%87%0.7063
口语（同批改写）4072.50%66%0.5792

三组数放在一起读，能读出三件事，第三件才是关键。

逐一读这三个数
第一
命中率从 77.50% 掉到 72.50%，掉了 5 个点。看着还能接受——法条大多还在前 5 里。
第二
首位命中从 87% 掉到 66%，掉了 21 个点。同一个模型、同一批题，只是把问法改成口语，排第一的能力塌了一大截。
第三
语义鸿沟主要伤排序，不只伤召回。法条被找到了，但被挤到后面。这一条直接决定了后面优化重点：不只是「多召回」，更是「让对的排前面」。

第三件事为什么重要？如果只看命中率，你会以为问题不大、掉 5 个点而已。但下游是「取前 N 条塞进 prompt」，排第 5 和第 1 对最终答案的影响完全不同——排后面意味着上下文里塞了四条噪声，模型更容易被带偏。

未命中不等于模型差。口语那 40 条里有 7 条，两种问法都失败。翻回去看标注，是标错了——家暴那题标到了《反家庭暴力法》第一条（立法目的条款），怀孕拒录那题标到了村委会的义务条款。归因时必须留「标注问题」这一类，否则你会拿一个错的标准去优化模型。

这组数的两个前提，别忘了

  • 口语版只有 40 条，是人工改写的样例，噪声不小。它能说明方向（口语确实掉点），但不足以支撑「提升 2 个点就算成功」这种细判断。要拿它当基线，得把 400 条全改成口语再跑一遍。
  • 基线是「不微调时的成绩」，必须在你写第一行训练代码之前跑出来。训完再补基线，等于先看到结果再定标准。
这一章钉住了三件事
  • 钉住了：尺子挂在下游，三个读数分别是命中率、首位命中、MRR，各管一件事
  • 不这么做会：只看命中率，得出「只掉 5 个点，问题不大」的结论，错过「排序塌了 21 个点」这个真正的问题
  • 下次遇到同类问题，先问：我这个指标能不能区分「找到了」和「排得前」——分不出来的指标，指导不了优化
带走命中率说有没有，首位说排得前不前——两个数一起看，才知道该往哪儿使劲。

4需求落成一句话：一份只做翻译的契约

结论需求写得越短越难被曲解。这个项目的需求四行就够：输入什么、输出什么、绝不做什么、拿什么量。四行里最容易被删掉的是第三行，而它恰恰是最该守住的。
需求契约 · 法律问题改写器
输入
一句生活语言的法律问题。实测平均 68.6 字，中位 62 字——大多数用户就一句话，不问第二遍
输出
一段法条语体的检索用文本，不超过 220 token。要求含核心法律概念、可能的法律关系、责任类型；不写建议、不写结论
不做
不回答用户、不给建议、不写「建议您」、不推理案件结果、不做多轮
量什么
hit_rate@5，基线 72.50%（口语 40 条）；训练目标是在同一套题上把它抬起来

为什么「不做」是设计，不是偷懒

一旦它开始回答问题，三件事同时崩：

崩在哪具体怎么崩
没法评测答案对不对要人眼看，hit_rate 立刻失效。你会从「有一个客观数」退回到「感觉还行」
和下游抢活链路里已经有一个大模型负责答，1.7B 去答只会更差。两个模型都在答，出错了不知道怪谁
责任变重输出检索文本，错了是检索偏；输出法律意见，错了是给人指错路。法律场景里这两件事的量级不一样
一个真实的诱惑训到一半你一定会想：「反正它已经懂法条了，让它顺手给个建议不是更好？」——忍住。加一句话，训练目标就要跟着加，评测就要人眼看，前面攒的客观指标全作废。范围是一点点放开的，不是一次放开的。

把四个空填一遍

上一课给的需求四问，这里按本项目填一遍，你会发现它填得出奇地快——因为前面两章已经把证据摆齐了。

问什么本项目的答案
谁在什么场景失败普通用户，在手机端问一句大白话法律问题——没有律师、没有法条编号，只有生活里的说法
现在怎么失败断在「取资料」：口语问法命中率 72.5%，首位只有 66%，对的法条被挤到后面
做成什么样算解决同一套口语题，hit_rate@5 抬起来，且首位命中同步改善——只抬命中率不抬首位，说明只是多捞了几条
这次不做什么不答问题、不建议、不做多轮、不跨法域（一期只覆盖民法典为主的 50 部法）

四行填完，需求就从一段描述变成了一份可以对照验收的契约。三个月后有人问「这个模型是干嘛的」，你把这四行发给他，不用解释。

这一章钉住了三件事
  • 钉住了：需求 = 输入 + 输出 + 不做 + 指标，四行，一页
  • 不这么做会：范围在训练过程中一点点放开，最后训出一个什么都会一点、什么都测不准的模型
  • 下次遇到同类问题，先问：我这个模型的「不做」有哪几条——一条都说不出来，说明范围还没定
带走需求的价值不在写了什么，在明确不做什么——边界越清楚，评测越硬。

5数据从哪来：三类来源，和这套为什么能用

结论数据来源只有三类：自己标、拿开源的、让模型造。三类各有代价，先认代价再挑——开源看起来最省事，代价是你得接受别人的分布。
来源好在哪代价是什么什么时候选它
自有标注分布完全贴合线上，质量可控慢、贵；标 3 万条要有预算和标注规范开源数据分布差太远，且任务足够重要
开源数据当天就能拿到，规模大分布是别人的；字段结构未必对得上你的任务任务通用、能找到字段对得上的数据集
模型合成要多少有多少，成本低会把自己的错学回去；质量随模型上限封顶做冷启动，或补充长尾情况

这个项目走的是第二条。理由很实际：我们要学的东西——「一句话法律问题对应哪几条法条」——恰好是别人已经标好的，而且标得比我们能负担的规模大得多。

手上这三份，各自的角色不一样

文件条数结构在本项目里的角色
DISC-Law-SFT-Triplet23,331法条 + 问题 + 答案训练对的来源。它的 reference 就是「这题该命中哪条法条」的标注
DISC-Law-SFT-Pair79,692问题 + 答案基本不用。只有答案没有证据链，学不到「法条怎么写」
DISC-Law-Eval2,563 + 300客观题 + 主观题只做遗忘检测：微调前后各测一次，看通用法律能力掉了多少

三份加起来 171 MB，已经全部下到本地。为什么 Triplet 珍贵：它把「这道题该命中哪条法条」标出来了，等于有人替你把金标准做好了。没有这份标注，你手上只有一堆「问题 + 答案」，那就得自己回去查每条答案引的是哪一条法条——3 万条，人工做不了。

Pair 那 79,692 条为什么不用，值得说清楚。它的问题是「问题 → 答案」，能训出一个会答法律题的模型。但我们要的不是会答，是会「换个说法」。拿它训，训出来的是第 1 章那张图里第五格的东西——下游大模型已经在干这个了，而且干得更好。数据量大不等于该用。

「能用」不等于「直接能用」

接下来三章干一件事：把这 23,331 条拆开看。因为这份数据的原始用途是「给模型法条，让它答」，而我们要的是它的另一半信息——「这个问题对应哪些法条」。同一份数据，换个方向用，字段的角色全变了。方向换错，训出来的东西就不是你要的。

这一章钉住了三件事
  • 钉住了：三类来源各有代价；本项目选开源，图的是别人已经标好了「问题对应哪条法条」
  • 不这么做会：看到 8 万条 Pair 就拿来训问答，训出一个和下游抢活、还没法评测的模型
  • 下次遇到同类问题，先问：这份数据的原始用途是什么，我要的那部分信息在哪个字段里
带走数据不是拿来就用，是先看它原本为谁而做——用途反了，字段的意思全反。

6摊开一条 Triplet：四个字段到底是什么关系

结论这份数据最容易被误读的地方，是它没有一个字段叫「用户问题」。四个字段是一套拼装关系，不是四列独立信息——读懂这套关系，才知道哪一块能进训练。

抽第一条真实样本来看。它讲的是「合伙人退伙后能不能追偿」这件事，我们把四个字段原样摆出来。

把四个字段逐一说清「里面是什么、从哪来、能不能进训练输入」：

换个方向用这份数据的原始用途是「给模型法条，让它答」，所以它把法条和答案都摆进 input 和 output。我们要的是另一半——「这个问题对应哪些法条」。同一批数据，换个方向用，字段的角色全变了。方向换错，训出来的就不是你要的东西。
这一章钉住了三件事
  • 钉住了：四个字段是一套拼装关系，真正的「问题」只占 input 末尾 13.5%，藏在 <问题>： 之后
  • 不这么做会：把 input 整个当输入，模型学会的是「读法条、续答案」，不是「把口语翻成法条」
  • 下次遇到同类问题，先画字段关系图，再逐个问「它能不能当输入」
带走先搞清哪个字段是「问题」，哪个是「答案纸」——拿错字段当输入，训练方向整个反。

7三个陷阱：看起来能用，其实不能用

结论三个坑有一个共同点：都不会报错。训练照跑，loss 照降，上线才发现模型学会了抄法条。所以判断不能靠报错，只能靠一句口诀。

陷阱一：input 整段进，模型学会抄

如果把 input 原样当输入，模型 86.5% 的输入是法条原文。它学到的是「看着法条，续写后面的答案」。训练时法条就摆在眼前，它当然写得好，loss 一路降。

但线上推理时，模型面前只有用户那句大白话，没有法条。它没得抄，就开始凭记忆编——编出一个「看着像法条语体、其实引错条文」的结果。这不是效果差，是任务本身训错了。

处理办法很直接：把 <问题>： 之前的一切切掉，只留问题。脚本里就一行正则：

def extract_triplet_question(text):
    match = re.search(r"<问题>\s*[：:]\s*(.+)", text, flags=re.S)
    return match.group(1) if match else text

陷阱二：reference 混进输入，直接泄露

reference 是「这题该命中哪条法条」的答案纸。如果把它拼进输入，模型等于考试时把答案放在手边，它什么都「学得会」——因为它直接看到答案了。

泄露最阴险的地方是：它不会让训练变差，反而让 loss 更低。模型越学越顺，你以为训对了，其实它只是背下了答案纸。上线后没有答案纸，成绩瞬间塌掉。而且它不报任何错，你只能靠「这些字线上能看到吗」这句口诀把它揪出来。

口诀只有一句：这些字，线上推理时模型能看到吗？看不到的，一律别塞进训练输入。法条原文、标准答案、reference、未来的用户输入，只要推理时不在模型面前，就不能在训练时喂给它。

陷阱三：output 当目标，训出来的是问答模型

最后一个坑藏得更深：就算你切干净了 input、隔离了 reference，拿 output 当训练目标，训出来的还是错的——output 是「给用户的答案」，不是「法条语体的检索文本」。

区别在哪？看两种目标教出来的模型，线上会怎么输出：

拿 output 当目标 · 训出问答模型
「根据《民法典》第九百七十三条规定，合伙人对合伙债务承担连带责任，因此您有权向其他合伙人追偿，建议您……」
开始给建议、下结论——正好撞上契约里「不做」那三条，评测也彻底失效。
拼出法条语体当目标 · 训出改写器
「合伙债务 连带责任 合伙人退伙 清偿份额 追偿权 民法典第九百七十三条 合伙合同」
只吐概念和法条语义，不表态。检索器拿去一比，命中率就起来了。

三个陷阱排成一串，你会发现它们是同一件事的三面：input 里有法条、reference 是答案、output 是答案——这三块加起来，就是「别人已经帮你把答案准备好了」。你要做的，是把它们全部拦在训练输入之外，只留那个真正的问题，再自己拼一个新的目标出来。拼成什么样，第 9 章讲。

这一章钉住了三件事
  • 钉住了：三个陷阱的共同点是不会报错——loss 反而更低，所以只能靠口诀挡
  • 不这么做会：训出一个训练集上 99 分、上线一塌糊涂的模型，还找不到原因
  • 下次遇到同类问题，先问：这些字，线上推理时模型能看到吗
带走泄露不报错，loss 还更低——能拦住它的只有一句口诀，不是监控面板。

8数据的数字画像：23,331 条到底长什么样

结论23,331 条不是「够用」的意思。要看它的长度、覆盖、偏斜——这几个数决定 cutoff_len、决定训练多久，也决定它能不能撑起你要的任务。

先把长度分布量出来。这一列数看着平淡，它直接决定两个训练参数：能塞多长的样本、要截断多少。

字段（字符数）最小中位 p50p95最大说明
input 全长65460715910其中 86.5% 是法条，会被切掉
切出后的问题—62133—均值 68.6 字，和契约的输入对上
output 答案273205882,82172% 超过 220 字，必须截断

这三个数合起来讲了一个故事：input 看着长，是因为塞满了法条；真正的问题只有 62 字。而 output 有一长尾，最长的能到 2,821 字。于是两个训练决策立刻浮出来：

  • cutoff_len 看的是切完之后的长度。输入就 62 字、目标几百字，加系统提示，几百 token 够用。别拿 input 的 910 字去定上限，那是被法条撑大的假象。
  • 目标文本必须截断。契约说输出 220 token，而 72% 的答案光字数就超 220 字，token 数只多不少。不截断，一半样本会被硬塞进一个装不下的框。

再看覆盖和偏斜

法条库是从 23,331 条的 reference 里抽出来、去重后的结果：6,432 条法条，覆盖 50 部法。但覆盖不等于平均，看前几名就明白：

法律法条数占比意味着什么
民法典1,25719.6%绝对主力，样本最足，训得最熟
刑法4487.0%第二梯队
刑事诉讼法3064.8%长尾开始，每部法样本都不多
民事诉讼法2894.5%长尾，一路拖到冷门小法
海商法2764.3%同上，语体覆盖会明显偏薄

偏斜的后果很实际：民法典那 19.6% 会训得最好，冷门法的样本少，模型对它们的语体就不熟。这不是「数据有问题」，是「数据长这样」，得提前知道——免得训完拿一道冷门法域的题一测，还以为模型崩了。

还有一条常被漏看的：每条样本平均对应 3.2 条法条（中位 3，最多 8）。一条问题常常不是对应一条法条，而是跨几条。这意味着训练目标不能只给一条，得把好几条的信息都带上——这又反过来要求目标文本更长一点，和上面「截断」形成一对要平衡的力。

最关键的一句这批数据不缺数量，缺一列——它没有「人话 → 法条语体」的现成配对。它有的是「问题 + 法条 + 答案」的三角。所以它只能支撑「从问题到法条」的映射，支撑不了「从问题到答案」。缺的这一列，直接决定任务是什么。
这一章钉住了三件事
  • 钉住了：真正的问题 62 字，答案 72% 超 220 字，法条覆盖 50 部但严重偏向民法典
  • 不这么做会：拿 input 全长定 cutoff_len、不截断目标、无视偏斜，训练和评测都会栽在没预料到的地方
  • 下次遇到同类问题，先量长度分位、覆盖占比、每条样本的目标个数三个数
带走数据画像不是统计爱好，是训练参数的依据——长度定 cutoff，偏斜定预期。

9缺的那一列，决定任务只能是改写

结论数据缺什么，任务就只能是什么。这一章把缺口补成训练目标——用 reference 和 output 拼出一段「假设性法条文档」，让模型学「法条怎么说」，而不是学「怎么答」。

把缺口说死：我们要的是「口语问题 → 法条语体文本」的配对，数据给的是「法条 + 问题 → 答案」的三角。缺的正是中间那个箭头——没有一段现成的、能直接当训练目标的法条语体文本。

但数据里有原料：reference 是法条原文，output 是围绕这些法条的讨论。把两者拼起来，就是一段「带法律概念和法条语义」的文本——恰好是我们想要的检索用文本的样子。拼法如下：

# 目标文本 = reference 全部法条原文 + output 答案，拼成一段，截到 700 字
ref_text = " ".join(ref for ref in item["reference"])
target  = ref_text + " " + item["output"]
target  = target[:700]

为什么这么拼，拆开看：

拼什么贡献了为什么需要它
reference 打头法条原文的措辞、条文号、法律术语这是模型要学的「法条怎么说」——目标里必须有它，模型才知道往哪个语体上靠
output 接后面「这个问题在法律上怎么被讨论」的语感光有法条太干，接一段答案补上语义衔接，检索时更贴近真实讨论
截到 700 字控制目标长度，压住长尾不截的话，2,821 字那种样本会拉爆训练长度

拼完的长相，拿第 1 条样本看一眼——训练目标是左边这样（片段），而不是右边那个「答案」：

目标文本（进训练）：《民法典》第九百七十三条：合伙人对合伙债务承担连带责任。
清偿合伙债务超过自己应当承担份额的合伙人，有权向其他合伙人追偿。……
根据《民法典》第九百七十三条规定，合伙人对合伙债务承担连带责任……

这个方法有个专门的名字，叫 假设性文档嵌入（HyDE, Hypothetical Document Embeddings）。核心想法一句话：不让模型答问题，让它「编」一段假想的法条文本，拿这段文本去检索。它成立的原因很简单——检索器比的是「像不像法条」，不是「答得对不对」，所以模型编得越像法条，命中越好。

为什么 HyDE 能治这个病检索的难点从来不是「模型不懂法」，是「用户的话和法条的话不是一个语体」。HyDE 逼模型先把用户的话翻译到法条语体里，再拿译文去检索——两段同语体的文本相比，相似度才真正可比。

到这里，三样东西闭环了

环节它说了什么怎么落在任务上
需求断在取资料，要改 query 侧输入是口语问题，输出是法条语体文本
数据只有「问题↔法条↔答案」三角缺的配对，用 reference + output 拼出来
任务只能是改写，训不成问答HyDE：口语 → 假设性法条文档 → 检索

三个环节互相咬合，没有一个是「挑」出来的。需求说「要翻译」，数据说「只能翻译」，任务就只能是翻译——这是前四环最想教你的一件事：任务不是拍脑袋选的，是被需求和数据夹出来的。

这一章钉住了三件事
  • 钉住了：目标文本 = reference 法条 + output 答案，截到 700 字；这就是 HyDE 的训练标签
  • 不这么做会：拿 output 当标签，训出问答模型，上线后开始给建议、撞契约红线
  • 下次遇到同类问题，先问：数据缺的那一列，我能不能用现有字段拼出来
带走任务不是选出来的，是被需求和数据夹出来的——拼不出来的任务，说明数据还不够。

10小结：两样东西到手，才谈得上训练

结论这一课交出去两样东西：一句话的需求契约，一份说得清来历与缺口的数据画像。两样都在纸上，训练才不是碰运气。

把这一课串起来，是一条没有任何跳跃的链：

需求 → 数据 → 任务，三步没有一步是拍脑袋
第一步
系统断在「取资料」，归因实验证明是 query 语体对不上——所以要在入口做改写
第二步
基线量出缺口：口语首位命中 66%，比书面低 21 个点——所以尺子挂 hit_rate@5
第三步
数据缺「人话→法条语体」配对，只能用 reference + output 拼——所以任务只能是 HyDE 改写

数据侧八问自检

离开这一课前，拿下面八个问题问一遍自己手上那份数据。答不上来的，先别急着开训。

#问题答不上来的后果
1它原本是为谁、为什么任务做的方向用反，字段全读错
2哪个字段是「问题」，哪个是「答案纸」拿答案纸当输入，直接泄露

四条边界，越界就返工

  • 需求还没定段，不碰数据。不知道断在哪，看数据等于在黑暗里数钱。
  • 没跑基线，不定目标。「抬起来」是废话，抬几个点、从哪个数开始抬，才是需求。
  • 答案纸、法条原文，一律不进输入。这条没有例外，也没有「只漏一点点」。
  • 范围只做减，不做加。任何「顺便让它也……」都是危险信号。
这门课留下的判据
  • 需求侧的判据：能不能一句话说清「断在哪一段」，能不能把「解决」翻译成指标
  • 数据侧的判据：每个字段能不能当输入，能不能拼出缺失的配对，覆盖和偏斜心里有数
  • 任务侧的判据：它是被需求和数据夹出来的，不是选出来的——夹不出来，说明前面有一步没想清
带走看清病、看透料，任务自己会浮出来——训练是后面的事，这一课的正题是把前两件事钉死。
