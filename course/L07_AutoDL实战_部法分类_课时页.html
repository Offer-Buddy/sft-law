4LLaMA-Factory 是什么

结论一个社区开源的全流程训练框架：训练、推理、导出、起 API 都收在 llamafactory-cli 一条命令下，配置靠三件套——yaml 管怎么练、注册表管数据在哪、模板管对话怎么拼。

镜像里自带它，但「自带」不等于「会用」。先看一次训练到底要凑齐什么：

一个命令，六个动作

和 ms-swift 一样靠子命令分派，只是名字不同：

命令干什么本课用不用
llamafactory-cli train训练，读 yaml用，第 7 章起训
llamafactory-cli chat命令行里跟模型对话用，第 9 章手测
llamafactory-cli export合并 LoRA，或导出量化版可选，要交整模型时才用
llamafactory-cli webui开网页界面，点选配置用，第 6 章先点一遍
llamafactory-cli api起一个 OpenAI 兼容接口不用，部署课再说
llamafactory-cli version打印版本号用，第 3 章已经验过

三件套各管一件事

新手最容易把三个文件混成一个问题，其实它们分工很清楚：

文件 / 参数回答哪个问题写错了会怎样
cls_qlora.yaml怎么练参数名写错直接报错；值写错只是练得差，不报错
dataset_info.json数据在哪报 dataset not found，连训练都起不来
template对话怎么拼名字错就报错；名字对但选错模型，只让 loss 变慢
stage 是 yaml 里最该先看的一行它决定这次干哪类训练：pt 继续预训练、sft 监督微调、dpo / kto / orpo 偏好对齐。本课写的是 stage: sft。看别人的 yaml 卡住时，先看这一行对不对——它一错，后面几十个参数全白填。

它还有一张脸：WebUI

除了命令行，这个项目还带一个网页界面：llamafactory-cli webui，点选就能训练，还能把点出来的配置导出成 yaml。两条路操作的是同一套参数——界面是外壳，yaml 是去掉外壳的样子。

本课两条都用，顺序是先界面后 yaml：第 6 章先把参数在页面上点一遍、看见 loss 动，顺手导出一份 yaml；第 7 章再拿这份 yaml 逐行拆，讲清每个数为什么是这个值。先有画面，再落文件。

它踩在谁肩上

框架本身不发明训练算法，是把几个库串起来：transformers 加载模型、peft 挂 LoRA、trl 管训练循环、accelerate 管显存与多卡，再加 unsloth 提速。

所以报错里出现这些库名是正常的，别以为装错了东西——那是底层在说话。判断方法：报错里出现 peft / trl，问题在方法层；出现 torch / CUDA，问题在环境层。

  • 一个命令六个动作，本课只用 train 和 chat。
  • 三件套缺一不可：yaml 管怎么练、注册表管数据在哪、模板管对话怎么拼。
  • stage: sft 是 yaml 第一行该确认的东西。
一句话带走框架不替你做决定，它只负责执行——三件套写对了，剩下的事它一件都不会漏。

5准备数据

结论转成 instruction/output 两字段，放进 data/，再在 dataset_info.json 里注册一行——三步缺一不可。

本地先导出（L06 已经跑过这条命令，产物是一样的）：

# 在本地项目根目录执行，生成 llama-factory 与 ms-swift 两套数据
python scripts/export_platform_data.py
# 看导出的文件：cls_train.jsonl、cls_val.jsonl、dataset_info.json
ls data/cls/export/llamafactory/

LLaMA-Factory 认的是另一套字段名。同一个样本，两个平台的写法对照：

ms-swift 吃的：query / response
{"query": "请判断…问题：小王是…", "response": "个人独资企业法"}
字段名固定，框架按这个名字找。
LLaMA-Factory 吃的：instruction / output
{"instruction": "请判断…问题：小王是…", "input": "", "output": "个人独资企业法"}
多一个空 input，是 alpaca 格式的固定位。

上传并注册

把 cls_train.jsonl 和 cls_val.jsonl 传到 /root/autodl-tmp/LLaMA-Factory/data/。

考卷 test_eval.jsonl 放到 /root/autodl-tmp/eval/，训练全程不碰它。

项目里的 scripts/eval_cls.py 也传一份到 /root/autodl-tmp/sft-law/scripts/，最后一章验收要用它。

然后在 data/ 里的 dataset_info.json 加两行：

"cls_law": {
  "file_name": "cls_train.jsonl",
  "columns": { "prompt": "instruction", "response": "output" }
},
"cls_law_val": {
  "file_name": "cls_val.jsonl",
  "columns": { "prompt": "instruction", "response": "output" }
}
columns 这一行在干什么告诉框架「我文件里 instruction 这个字段，就是你要的 prompt」。字段名和框架默认一致时可以不写，但写上更保险——换个数据集字段名不一样时，改这一行就行，不用动文件。

注册完验一眼，注册名和文件都在：

  2292 .../cls_val.jsonl
  2292 /root/autodl-tmp/eval/test_eval.jsonl
$ python -c "...print(list(d))"

三处最容易错的地方① 文件放在 data/ 之外（file_name 是相对 data/ 的）；② JSON 里多一个逗号导致整个文件解析失败，训练会直接报 dataset not found；③ 改了 dataset_info.json 没重启 notebook 进程，读的还是旧缓存。
  • 两个平台字段名不同，互转只改字段名，不动内容。
  • dataset_info.json 是「注册表」，不注册框架就找不到文件。
  • 文件必须在 data/ 下，file_name 写相对路径。
  • 考卷 test_eval.jsonl 单独放、不注册、不参与训练。
一句话带走换框架时先看它「认哪些字段名」——数据本身一个字都不用改，改的是映射。

6先在界面上点一遍

结论起训前先开 WebUI（网页界面）把参数点一遍：两分钟看见 loss 动，顺手导出一份 yaml——下一章那个文件就是从这儿来的。

LLaMA-Factory 带一个网页界面（Gradio 搭的，用 Python 写网页的库），四个页签：训练、评估与预测、对话、导出。它和后面的 yaml 动的是同一套参数——界面是外壳，yaml 是去掉外壳的样子。

本地一条 llamafactory-cli webui 就开，默认 7860 端口。但 AutoDL 只对外放 6006 一个口做「自定义服务」，7860 打开是空白页——这是多数人第一次点不开的原因，不是装坏了。

页面长什么样

从上往下四层：模型（语言、模型名称、微调方法）、页签（Train / Evaluate & Predict / Chat / Export）、数据（训练阶段、数据路径、数据集、预览按钮）、参数（学习率那一整排）。LoRA 秩与 α、量化、验证集、对话模板、输出目录全收在折叠的「高级设置」里。

截图比镜像老官方这张图还是 LLaMA3-8B 时代的布局，新版把「模型名称」与「模型路径」合成了一个框，高级设置里多了「加速方式」。位置会挪，五组内容不会少；图也停在「截断长度」那一排，按钮区和右侧日志框在页面更下方。

三条最容易踩的坑

现象真正的原因怎么改
数据集下拉框是空的dataset_info.json 没注册，或 JSON 多了个逗号整份解析失败python -c "import json;json.load(open('data/dataset_info.json'))"

导出 yaml：这才是界面的正事

底部的 Preview command 显示「这堆点选等价于哪条命令」，旁边按钮存成 yaml——那就是下一章 cls_qlora.yaml 的底稿。但导出后有三处必须手改：

导出之后要过的三关
① 预热
界面给的是 warmup_steps（绝对步数，默认 0），yaml 要的是比例 warmup_ratio: 0.05——0.05 × 2294 ≈ 115 步，别留 0
② 数据集
dataset 存的是下拉框里的注册名，改过 dataset_info.json 的键名就对不上，要手改成 cls_law
③ 缺项
界面没填的字段不会出现：plot_loss、save_total_limit、preprocessing_num_workers 都得补

什么时候该离开界面

只有一次、不需留痕的场合用界面：第一次上手、调参前探路、给不写代码的人演示。要跑第二次、要比两组参数、要交给同事复现——配置本身成了交付物，就回 yaml。

  • AutoDL 上界面要走 6006，7860 是空的——不是装坏了。
  • 四个默认值必须改：学习率 5e-5、截断 2048、秩 8、计算类型 fp16。
  • 导出 yaml 只到七分熟：预热方式、数据集名、缺项三处要手补。
一句话带走界面负责让你看见，yaml 负责让你能改。

7一个 yaml 起训

结论把 L06 那串命令行参数翻译成一个 yaml，然后 llamafactory-cli train 一条命令起训。

cls_qlora.yaml

### 模型
model_name_or_path: Qwen/Qwen3-1.7B   # 不加 -Instruct，它就是指令版
trust_remote_code: true               # 允许加载仓库自带建模代码

### 方法
stage: sft                            # 监督微调，不是 pt 也不是 dpo
do_train: true                        # 真训练；false 就只做预测
finetuning_type: lora                 # 只训低秩补丁，基座不动
lora_rank: 16                         # 补丁宽度，本任务 16 够
lora_alpha: 32                        # 配 r=16 得 α÷r=2 的惯例比例
lora_target: all                      # 注意是 all，ms-swift 那叫 all-linear

### 数据
dataset: cls_law                      # 用注册名，不是文件路径
eval_dataset: cls_law_val             # 不给就没有 eval_loss
template: qwen3                       # 必须和基座配，写错会静默变差
cutoff_len: 512                       # 截断长度，问题最长 333 字
preprocessing_num_workers: 8          # 预处理进程数，纯 CPU 活

### 输出
output_dir: /root/autodl-tmp/saves/qwen3-1.7b/cls   # 数据盘，关机才不丢
logging_steps: 20                     # 每 20 步打一行日志
save_steps: 1147                      # 一轮存一次；想看出峰在哪，调细到 1/8 轮
eval_steps: 200                       # 每 200 步验一次，越密越慢
eval_strategy: steps                  # 按步验，不是按轮
save_total_limit: 3                   # 只留最近三个，不是最好的三个
plot_loss: true                       # 顺手画 training_loss.png

### 训练
per_device_train_batch_size: 8        # 单卡一次 8 条
gradient_accumulation_steps: 2        # 攒 2 次再更新，有效 batch 16
learning_rate: 2.0e-4                 # QLoRA 常用档，能一票否决
num_train_epochs: 2.0                 # 两轮，合计 2294 步
lr_scheduler_type: cosine             # 余弦衰减，末段步子变小
warmup_ratio: 0.05                    # 前 5% 步数升温，防推歪
bf16: true                            # 用 bf16，省掉 fp16 的 loss scale

### QLoRA：两条一起才叫 QLoRA
quantization_bit: 4                   # 基座压到 4bit 存放
quantization_method: bnb              # 用 bitsandbytes 做量化

### 加速
use_unsloth: true                     # 报 unsloth 相关错误就把这行注掉

对完这张表你会发现：参数几乎一一对应，变的只是写法——一个写在命令行，一个写在文件里。

2294 步是怎么来的

yaml 里根本没有 max_steps 这一项。你填的是 num_train_epochs: 2.0，步数是框架替你算的：

# 一轮多少步：训练集条数 ÷ 有效 batch，向上取整
18338 ÷ (8 × 2) = 1146.125  →  1147 步
# 两轮合计
1147 × 2 = 2294   # 日志里的 total_steps
epoch 是「过几遍」，step 是「更新几次」epoch 是进度（0 到 2 之间的小数），current_steps 是已经更新了多少次。current_steps: 20 时 epoch: 0.017，就是 20 ÷ 1147——两个数是同一件事的两种刻度。
别拿「步数够不够」当判据2294 不是目标，是两轮的自然结果。够不够只看 eval_loss 还在不在降：还在降就是没学够（加一轮），走平或抬头就是该停。真要手填 max_steps，只在续训或短跑试水时用。

超参数对照：那八组在 yaml 里叫什么

起训要填的超参数一共八组——就是 yaml 里那些要你亲手填的数字（学习率、轮数、batch、LoRA 容量），按改完之后影响什么分成三堆：改结果、改成本、改判断。位置固定，对号入座即可。

超参数yaml 字段改了会怎样
学习率 + 预热learning_rate / warmup_ratio学得多快。唯一能一票否决的超参数，偏大崩、偏小学不完
LoRA 容量lora_rank / lora_alpha / lora_target补丁能装多少东西。本任务输出一个词，r=16 已富余
有效 batchbatch × gradient_accumulation_steps梯度多稳。改它就得同时看学习率，否则不可比
截断长度cutoff_len短了切掉标签，长了白占显存
数值精度bf16换 fp16 要配 loss scale，还容易出 nan
梯度检查点gradient_checkpointing省三成显存，慢两成；显存够就别开
验证频率eval_steps / eval_strategy看多细对多久跑完——这项最花钱
保存间隔save_steps / save_total_limit一个 40 MB，别心疼盘；上限设小了会先删掉最旧的——而峰常在中间

新平台上最容易漏掉的是「验证和训练不同价」：实测训练 0.86 秒一步，一次验证要 208 到 286 秒。

按 eval_steps: 200 算，一轮只验 6 次，比每 100 步验一次省下约一半时间。代价是曲线粗一些，但判断「走平没有」够用。

改 batch 要连着改学习率有效 batch 翻倍而 learning_rate 不动，等于偷偷把步子放大一倍。要么按比例一起调，要么这次只改一项——两件事一起改，结果变好你也不知道是谁的功劳。

同样是形态示意（数按 ms-swift 那轮实测抄的，LLaMA-Factory 的字段名换成 current_steps）：你的数会不一样，盯 eval_loss 的走向就行。

Unsloth 与 QLoRA 同时开报错部分镜像里的 Unsloth 版本与 4bit 量化会打架。真撞上报 unsloth 相关错误，把 use_unsloth 那行注掉（前面加 #）再跑——慢一点，但能跑完。
  • yaml 是「参数换了个写法」，内容和命令行版本一一对应。
  • eval_strategy: steps + eval_steps 才让验证指标定期打印。
  • 超参数分三堆：改结果、改成本、改判断——一次只改一个，结论才可比。
  • 验证比训练贵得多，eval_steps 定密了等于给同一件事多付一倍钱。
  • Unsloth 与 4bit 打架就注掉那行，能跑完比跑得快重要。
一句话带走配置文件不是另一种知识，它只是把命令行参数抄进了文件——看不懂 yaml 时，逐行翻回命令行就懂了。

8看 loss 拿 adapter

结论产物结构和魔搭一模一样，只是路径在数据盘；日志看 trainer_log.jsonl 的 eval_loss，选对率同样要回 test 集上测。
/root/autodl-tmp/saves/qwen3-1.7b/cls/
├── checkpoint-1147/                 # 第 1 轮结束
│   ├── adapter_config.json          # LoRA 配置
│   └── adapter_model.safetensors    # 补丁权重，约 40 MB
├── checkpoint-2294/                 # 第 2 轮结束
├── training_loss.png                # plot_loss 画出来的曲线

挑 checkpoint 的思路和 L06 一致，只是日志文件换了名字——LLaMA-Factory 自己写 trainer_log.jsonl，步数字段叫 current_steps。

一行命令拉成表：

# 进输出目录，trainer_log.jsonl 就在这里
cd /root/autodl-tmp/saves/qwen3-1.7b/cls
# 把每条 eval 记录抽成「步数 + eval_loss」两列
python - <<'PY'
import json
rows = [json.loads(l) for l in open('trainer_log.jsonl') if l.strip()]
for r in [x for x in rows if 'eval_loss' in x]:
    print(f"step {r['current_steps']:5d}  eval_loss {r['eval_loss']:.4f}")
PY
$ python - <<'PY'
step   200  eval_loss 0.1117
step   400  eval_loss 0.0878
step   600  eval_loss 0.0713

数字是形态示意（步长 200 对应 yaml 里的 eval_steps）。checkpoint-1147 的 1147 就是表里的 step。

判读和 L06 一样：看 eval_loss 是还在降还是已经上抬，别看 token 级的花哨数字。

两个框架报的不是同一个数ms-swift 报 eval_token_acc（逐 token 命中率），LLaMA-Factory 默认只报 eval_loss，开了生成式评测才会多出 bleu、accuracy 这类字段。名字和算法都不一样，两平台的数不能直接横着比——要比就比第 9 章同一份脚本测出来的 accuracy。
不用逐个目录进去翻分数不在目录里，全在 trainer_log.jsonl。目录名就是步数，ls -d checkpoint-* 和表里的 step 一列对上即可，挑中哪个才进去打包。
yaml 里 save_steps 为什么是 11471147 正好一轮的步数，所以每轮结束存一个：checkpoint-1147（1 轮末）和 checkpoint-2294（2 轮末）。存成 200 步一次、只留最近两个，最后剩下的是相邻两个快照，几乎同一个模型，比了等于没比。写 save_strategy: epoch 等价且不用算步数。
更通用的做法：对齐 eval + 自动回最优轮数多（5 轮以上）时，按轮存会攒一堆；更常见的是 save_steps 与 eval_steps 设成同一个数、save_total_limit 给 3，再加 load_best_model_at_end: true 配 metric_for_best_model: loss——训完框架自动把最优权重摆回output_dir，你不用挑。
load_best_model_at_end 挑的不一定是你要的那个它按 metric_for_best_model 挑，而分类任务里这个字段只能填 loss——你要的却是「50 选 1 选对率」。两者通常同向，但没有保证：loss 还在微降、选对率已经走平甚至回落，是这个规模上很常见的一段。要按选对率挑，就得训完拿 val 逐个 checkpoint 打分（L08 第 3 章那套扫法）。
「细存」的坑不在存得细，在留得少save_steps: 200 配 save_total_limit: 2 才是白存——只剩两个相邻快照，几乎同一个模型。配上不设上限就完全不一样：11 个点铺满两轮，峰在哪一眼就看出来。LoRA 一个快照 40 MB 上下，11 个不到 500 MB，盘不是问题。要省，开 save_only_model: true（只存权重、不带优化器），代价是这份快照不能用来续训。
# 两个都带走，一共 80 MB；比的是 1 轮 vs 2 轮
cd /root/autodl-tmp/saves/qwen3-1.7b/cls
ls -d checkpoint-*
# checkpoint-1147  checkpoint-2294
tar -czf cls_adapter.tar.gz checkpoint-1147/ checkpoint-2294/
存在系统盘上默认 output_dir 若写在 /root/ 下，关机后可能随系统盘一起被释放，白训。所有产出都写进 /root/autodl-tmp/——那是数据盘，关机还在。
  • 产物结构与 ms-swift 完全一致：配置 + 补丁权重 + 日志。
  • 日志是 trainer_log.jsonl，步数字段 current_steps，判据是 eval_loss。
  • 两个框架报的指标口径不同，别横向比数字，要比就比同一份脚本测出的 accuracy。
  • save_steps 按轮设（1147），两个 checkpoint 才是「1 轮 vs 2 轮」。
  • 所有输出写数据盘，关机才不丢。
一句话带走两个框架产出的东西长得一样——因为 LoRA 的产物本来就只由「补丁」决定，跟谁训的无关。

9验它学会了

结论用同一份 test 集、同一个脚本，跑出与 L06 同口径的数字——这样两平台才可比。

先跑基线，再跑微调后。脚本和评测集都跟 L06 一样，两步都在 AutoDL 实例上跑——基线是对照组，换台机器就不是对照了。

# 1) 进项目目录，评测脚本在 scripts/ 下
cd /root/autodl-tmp/sft-law
# 2) 跑基线：--no-adapter 不加载补丁，测原始 Qwen3 的零样本水平
#    --limit 200 先跑 200 条试水，约 1 分钟，跑通再去掉
python scripts/eval_cls.py --no-adapter \
  --model Qwen/Qwen3-1.7B \
  --data /root/autodl-tmp/eval/test_eval.jsonl --limit 200

# 3) 跑微调后：--adapter 指向选中的 checkpoint，其余参数与基线一致
python scripts/eval_cls.py \
  --model Qwen/Qwen3-1.7B \
  --adapter /root/autodl-tmp/saves/qwen3-1.7b/cls/checkpoint-2294 \
  --data /root/autodl-tmp/eval/test_eval.jsonl
开机就先跑基线AutoDL 按时计费，别为跑基线单独开一次机：开机第一件事跑 --limit 200（约一分钟），确认脚本和路径通了，再传数据起训。已经训完的就在关机前补跑，模型权重下次开机要重下。
关键在「同口径」同一个 test 集、同一个 prompt、同一套 length-normalized 打分。换了一样就不叫对照——数字涨了也说明不了是模型变好还是尺子变松。
指标魔搭（L06）AutoDL（本课）怎么读
accuracy自己填自己填两个平台的差距应在一个点内
macro-F1自己填自己填差很多说明训练没收敛
top-3自己填自己填接近 accuracy 说明很有把握
用时 / 费用约 2 小时（A10，22 次验证）/ 免费约 1 小时（4090，11 次验证）/ 计时长 × 单价自己算一遍

两个平台训同一个任务、同一份数据，准确率应当非常接近。如果差出好几个点，先怀疑数据或超参不一致，别急着归因到平台。

忘了关 thinking 或没对齐模板手测时用 llamafactory-cli chat 要带 --template qwen3；模板不对，模型输出格式和训练时不一致，准确率会莫名其妙掉一截。
  • 同口径才能对照：同数据、同 prompt、同打分方式。
  • 两平台结果应接近；差很多先查数据与超参，再怀疑平台。
  • 手测也要对齐 template，否则输入格式和训练时不一样。
一句话带走可复现的判据是「别人换台机器跑出同一个数」——差在 0.5 个点以内，说明这条链真的通了。

10小结

结论两条链走完，你手里有两组可比的数字，和一张「什么是任务、什么是环境」的对照表。
层这次动了什么没动的部分
环境层换成 AutoDL 现成镜像，不装依赖GPU 型号一样是 24G
数据层字段名 query/response → instruction/output内容一条没改，还是 18,338 条
配置层命令行参数 → 一个 yaml超参数值逐个对应，一个没变
任务层无50 类分类、QLoRA、max_len 512 全部照旧

两个平台怎么选

不是「哪个更好」，是「什么时候用哪个」
选魔搭预算为零、第一次跑通、只需要验证「这条路行不行」——免费额度够用
选 AutoDL要连跑多次、要长期留环境、要换大模型——按小时付费比等免费额度划算
别做在两个平台间反复搬数据比效果——数据不动、任务不动，效果本来就该一样

三条边界

  • 产出不写数据盘关机后可能一起没，几小时白跑。
  • 不注册 dataset_info 就开训框架找不到文件，报错信息还容易误导你以为是路径问题。
  • 拿两个平台的不同口径比准确率数据集或模板不一样，比出来的差值是假的。

三条自检

每一步都能单独验，不用等全跑完
① 环境llamafactory-cli version 打出 0.9 以上
② 数据注册名在 dataset_info.json 里能查到，wc -l 对得上 18338
③ 结果本课 accuracy 与 L06 相差在 0.5 个点内，超了就回头看数据与模板
下一步两条链都通了，接下来该动「尺子」：把 test 集按部法拆开看，找出小类错在哪、混淆矩阵最亮的是哪一格——那才是调参的起点。
  • 换平台只动三处：镜像、字段名、配置形态；任务与数据不动。
  • 两平台结果应接近，差得远先查数据与模板。
  • 按小时计费的机器，跑完就关，产出写数据盘。
带走跑通两条链不算本事，能说清「哪一步换平台要改、哪一步不用改」才算真懂——那三处改完，剩下的原件照搬。
