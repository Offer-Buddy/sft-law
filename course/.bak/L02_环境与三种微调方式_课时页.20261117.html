把机器开起来，三个框架挨个认一遍

上一课五选已经定了：Qwen3-1.7B + QLoRA + 手写 transformers/peft + AutoDL 4090 + DISC-Law Triplet。这一课不讲为什么，只把这套选型开起来——配好依赖、验过显卡，再把 LLaMA-Factory、魔搭 ms-swift、手写三十行各跑一遍，做到「给哪个框架我都能上手」。

1定机器 2三个层次 3Factory 4ms-swift 5代码驱动
这一课要拿到的东西三档都过，才敢自己开训
档位你能做到怎么算达成
跑通在自己的机器或云上把环境配好，跑通一次最小训练torch.cuda.is_available() 为 True，三个核心包 import 不报错，产出一个 adapter 目录
分清说清三种方式各在哪一层，谁替代谁、谁能叠在谁上面白纸画出「底座 → 框架 / 加速 → 你的配置」三层，把三个名字放对位置
手写不靠框架，用 transformers + peft 写出三十行训练脚本三十行能跑通，print_trainable_parameters() 打出的是挂载的 LoRA 参数，不是全量
不处理：多卡并行、DeepSpeed / FSDP 配置、推理服务化（vLLM、TGI）、量化推理格式转换——这些不在主线里，遇到再说。

1先把机器定下来

结论平台上一课已经定了：AutoDL 4090 当主力、魔搭 A10 免费试跑。这一课不讲「为什么选它」，只讲「在它上面怎么把环境配起来」——依赖四层对上、验证三行过了，才算能开训。

AutoDL 上三个必须知道的点

踩过的人才知道
无卡模式
按 CPU 计费，很便宜。配环境、传数据、下模型都在无卡模式做，别开着 GPU 装包——光配环境就能烧掉几十块
盘的分工
系统盘 /root 小，数据盘 /root/autodl-tmp 大。几个 G 的模型放系统盘，会装到一半磁盘满
关机 ≠ 释放
关机保留磁盘（还收一点存储费），「释放」才清空。要复用环境，必须存成自定义镜像，否则下次重来

依赖是配套的，不是随便装

这四层版本必须对得上，从下往上装，不要跳：

层看什么对不上会怎样
显卡驱动nvidia-smi 右上角的 CUDA Version驱动太老，装再新的 torch 也调不动卡，只会退回 CPU
CUDA / torchtorch 版本要和驱动支持的上限匹配torch.cuda.is_available() 返回 False，或者一跑就 no kernel image
训练栈transformers + peft + trl + bitsandbytes新模型（比如 Qwen3 系列）需要足够新的 transformers，版本低了会报「不认识的模型类型」
框架LLaMA-Factory / ms-swift / Unsloth 各自锁自己的依赖范围三个装在一个环境里互相打架。见下面的坑
# 装完先验这三行，全过再往下走
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
python -c "import transformers, peft, trl, bitsandbytes as bnb; print(transformers.__version__, peft.__version__)"
nvidia-smi
最常见的两个死法。① pip install torch 装成了 CPU 版——一定要用官方给的 CUDA 版安装命令，别直接 pip。② 把 LLaMA-Factory、ms-swift、Unsloth 装进同一个环境，它们对 transformers 和 trl 的版本要求经常互相冲突。一个框架一个 conda 环境，这是纪律。
环境配超过一小时就换方案。这不是能力问题，是投入产出比问题——你花两小时修 CUDA，和你花两块钱开机跑一轮，后者才是在学微调。修环境修到怀疑人生的人，最后都没训出模型。
这一章钉住了三件事
  • 钉住了：依赖四层（驱动 → CUDA/torch → 训练栈 → 框架）从下往上装，验证三行全过才算能开训
  • 不这么做会：pip 装成 CPU 版 torch，或者三个框架塞进一个环境，互相打架、进度全停
  • 下次遇到同类问题，先看：驱动认不认、torch 是不是 CUDA 版、三个框架是不是各在各的环境
带走环境是门槛不是本事；过不去就绕，绕过去才算开始。

2三个名字，三个层次

结论LLaMA-Factory 和 ms-swift 是「框架」，帮你把数据加载、训练循环、导出、界面都包好；Unsloth 是「加速内核」，替掉底层的算子实现。前者管流程，后者管速度，不冲突。
关键一句三个一起学是浪费。正确顺序是：先看懂底层那三十行（第 5 章），框架就变成了「替你写这三十行」的快捷键。反过来先学框架，你会一直不知道 YAML 里的 lora_rank 到底改了什么。
名字是什么它替你做掉的事
LLaMA-Factory框架读数据、拼 prompt、挂 LoRA、跑训练循环、存 adapter、合并权重、开网页界面——全都包了
魔搭 ms-swift框架同上，另外多了和 ModelScope 模型库、免费算力 Notebook 的直连
Unsloth加速内核把 attention 和前向的那几个算子换成手写的更省显存版本；训练流程还得你自己写
这一章钉住了三件事
  • 钉住了：框架管流程，内核管速度，两者不在一个维度，可以叠着用
  • 不这么做会：把三个名字当成三选一的竞品，花一周各学一遍，底层还是没懂
  • 下次遇到同类问题，先问：这个东西是替我「省事」，还是替我「提速」
带走先看懂底层三十行，框架才是快捷键，不是黑箱。

3配置驱动一：LLaMA-Factory

结论它的价值就一条：不写 Python 也能训。代价是所有东西都藏进 YAML，你得知道那几个字段对应什么。

装与启动

git clone --depth 1 https://github.com/hiyouga/LLaMA-Factory.git
cd LLaMA-Factory
pip install -e ".[torch,metrics]"

# 两种入口，先用界面把流程走一遍
llamafactory-cli webui          # 打开网页，点着配
llamafactory-cli train sft_config.yaml # 用配置文件跑，可复现

数据：先注册，才能选

它不从命令行直接读文件，而是要求你在 data/dataset_info.json 里登记一个数据集名，之后 YAML 里用这个名字。这是新手第一个卡点。

// data/dataset_info.json 里加一条
"hyde_law": {
  "file_name": "hyde_law.json",
  "columns": { "prompt": "input", "response": "output" }
}

这个 columns 是把它自己的字段名，映射到你数据的字段名。你的数据长这样就不用改文件：

{"input": "老板让我天天加班不给钱", "output": "用人单位安排劳动者延长工作时间的，应当支付不低于百分之一百五十的报酬。"}

训练配置：真正要改的就这九行

model_name_or_path: Qwen/Qwen3-1.7B
stage: sft
do_train: true
finetuning_type: lora
lora_rank: 16
lora_target: all
dataset: hyde_law
cutoff_len: 1024
output_dir: saves/qwen3-1.7b-hyde

per_device_train_batch_size: 2
gradient_accumulation_steps: 8      # 等效 batch = 16
learning_rate: 1.0e-4
num_train_epochs: 3.0
对照这九行就是上一课那张概念图里的「参数层」：lora_rank 是 r、lora_target 是挂载层、cutoff_len 是 max_length、batch 与梯度累积是两个字段。YAML 不是新知识，是那六个旋钮的另一种写法。

它替你做的事，值得知道

  • 把 input + output 拼成带 chat 模板的完整序列，并自动把 prompt 段标成不算 loss
  • 按 cutoff_len 截断、能开 packing
  • 训完把 adapter 存到 output_dir，几十 MB，不是整个模型
  • llamafactory-cli export 能把 adapter 合回基座，产出一个完整模型目录
它的黑箱在这里：数据拼装。不同模型有不同的 chat 模板（Qwen 有自己的格式），模板选错不会报错，但效果会莫名很差——因为模型看到的不是你想要的对话结构。跑完先拿一条样本 decode 出来看一眼，确认「问题 + 答案」的拼接是你以为的样子。
这一章钉住了三件事
  • 钉住了：Factory 的用法就是「注册数据集 → 写九行 YAML → 一条命令」，界面是给你试参数用的
  • 不这么做会：数据没注册就去填 YAML，报「dataset not found」，然后开始怀疑人生
  • 下次遇到同类问题，先看：模板对不对、cutoff_len 够不够、batch 与累积乘出来是多少
带走YAML 里的每个字段，都是你在上一课学过的那个旋钮。

4配置驱动二：魔搭 ms-swift

结论和 Factory 是同类，能力对得上。它真正的优势不在功能，在网络和算力：国内直连下模型，配套免费 Notebook。
pip install ms-swift -U

# 一条命令开训，参数直接写在命令行
swift sft \
  --model Qwen/Qwen3-1.7B \
  --train_type lora \
  --dataset data/hyde_law.jsonl \
  --num_train_epochs 3 \
  --per_device_train_batch_size 2 \
  --gradient_accumulation_steps 8 \
  --learning_rate 1e-4 \
  --lora_rank 16 \
  --output_dir output/qwen3-hyde

和 Factory 的四个实际差别

方面LLaMA-Factoryms-swift
怎么配YAML 文件 + 网页界面命令行参数为主，也支持 yaml
数据怎么给先在 dataset_info.json 注册名字直接给文件路径，或注册数据集名
数据格式alpaca（instruction/input/output）或 sharegpt（messages）messages 或 query/response，字段名不同，要改映射
模型从哪来HuggingFace 为主，也支持魔搭默认走 ModelScope，国内不用配镜像也不卡
选它的理由如果你的痛点是「下模型老断」「没有卡但想试」，ms-swift + 魔搭的组合比 Factory 顺——它和社区是同一家，模型、Notebook、训练命令在同一个地方。如果你的痛点是「要给不写代码的人演示」，Factory 的网页更直观。
两个框架别混着记命令。它们参数名很像但不完全一样（--lora_rank 都有，数据参数一个叫 --dataset 一个是注册名）。真正要记住的只有一件事：数据字段怎么映射。换框架时 80% 的报错都出在这。
这一章钉住了三件事
  • 钉住了：ms-swift 和 Factory 能力同级，差别在配置方式、数据字段、模型来源
  • 不这么做会：把两套命令混着抄，跑不起来还以为是框架有 bug
  • 下次遇到同类问题，先看：这个框架要求的数据字段名是什么，你的 jsonl 对不对得上
带走选 Factory 还是 ms-swift，看你的卡和网，不看功能表。

5代码驱动：三十行，以及 Unsloth

结论框架替你写的就是这三十行。看懂它，你才知道 YAML 里那些字段在干什么；而 Unsloth 是在这三十行底下换引擎，不改变你写的东西。

手写版：4bit 加载 + 挂 LoRA

from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
import torch

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",              # 4bit 的量化方式
    bnb_4bit_use_double_quant=True,         # 量化常数再压一次
    bnb_4bit_compute_dtype=torch.bfloat16,   # 算的时候用 bf16
)

model = AutoModelForCausalLM.from_pretrained(
    "Qwen/Qwen3-1.7B", quantization_config=bnb, device_map="auto")
model = prepare_model_for_kbit_training(model)

lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
    task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora)
model.print_trainable_parameters()   # 会打印「可训参数占 1% 左右」

这四步对应的就是上一课那张 LoRA 图：基座压成 4bit（QLoRA）、冻结原权重、旁挂 A×B、只训那一小块。剩下的是把数据拼成序列、交给 Trainer 跑——那部分每个框架各写一遍，长得都差不多。

Unsloth 版：换掉这几行

from unsloth import FastLanguageModel

model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="unsloth/Qwen3-1.7B-unsloth-bnb-4bit",
    max_seq_length=1024, load_in_4bit=True)

model = FastLanguageModel.get_peft_model(
    model, r=16, lora_alpha=32, lora_dropout=0.0,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"])

注意区别：参数名几乎一样，但入口换成了 FastLanguageModel。它内部把 attention 和前向的算子换成了手写实现，所以同样的显存能开更大的 batch，或者同样的 batch 跑得更快。你的训练循环、数据、评估代码一行都不用改。

Unsloth 值得用的场景
单卡、显存吃紧
要反复试很多配置
模型在它支持列表里
能接受 Linux / WSL
省下来的时间是真的——试错轮次越多，收益越明显。
不建议硬上的场景
模型不在支持列表
只有 Windows 原生环境
要改模型结构
需要最新架构特性
它靠预置的算子实现换速度，模型太新或太偏，就得等适配。
别在 Windows 原生环境跟它较劲。它的加速依赖自定义 kernel 和 triton，官方支持的是 Linux；Windows 下要么走 WSL，要么直接用云。这和前面那条「环境配超过一小时就换方案」是同一条纪律。
这一章钉住了三件事
  • 钉住了：框架替你写的就是这段代码；Unsloth 换的是引擎，不是流程
  • 不这么做会：只会点界面，换框架或报错时完全不知道从哪查
  • 下次遇到同类问题，先看：print_trainable_parameters() 打出来是多少，对不上就是挂载层错了
带走先手写一遍三十行，之后用框架才叫「省事」，不叫「不懂」。
